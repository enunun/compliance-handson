# 第11回 権限の管理

この回では，AWSの権限を必要な分だけに絞り，その誤りを止めるゲートを作る．
CIからAWSへは，長期のアクセスキーではなく，OIDCで得る一時的な認証情報を使う．
あわせて，権限の棚卸しと，データベースのパスワードの交換を定期的な仕組みにする．


## 11-2 学ぶこと

### 最小権限と棚卸し

規格は次のことを求める．

- ISO/IEC 27001 A.5.15，A.8.2：アクセスは業務に必要な分だけ与え，特権は絞る．
- ISO/IEC 27001 A.5.18：アクセスの権利を定期的に見直す．
- SOC 2 CC6.1〜CC6.3：論理的なアクセスを制限し，与えた権利を管理する．

権限は，作るときに絞るだけでなく，定期的に棚卸しして，要らなくなったものを外す．

### IAMのポリシー

IAMのポリシーは，`Effect`，`Action`(操作)，`Resource`(対象)の組で権限を書く．
`"Action": "*"`や`"Resource": "*"`は，すべての操作や対象を許す．
ロールを引き受けられる者は，信頼ポリシー(`assume_role_policy`)に書く．

ポリシーをJSONのファイルに分け，OpenTofuの`templatefile`で読むと，ファイルを検査できる．
`${名前}`の部分には，`templatefile`に渡した値が入る．

```hcl
resource "aws_iam_role_policy" "app" {
  role   = aws_iam_role.app.id
  policy = templatefile("${path.module}/policies/app.json", { bucket_arn = aws_s3_bucket.app.arn })
}
```

### OIDCでの一時的な認証情報

GitHub ActionsはOIDCのトークンを発行できる(第6回)．
AWSにGitHubをOIDCのプロバイダとして登録し，ロールの信頼ポリシーでトークンの中身を条件にすると，ジョブはアクセスキーなしでロールを引き受けられる．
得られる認証情報は一時的なので，漏れても短い時間で使えなくなる．

信頼ポリシーでは，トークンの`sub`(どのリポジトリのどのブランチか)と`aud`を絞る．
`sub`を`repo:*`のように絞らないと，GitHubのどのリポジトリのジョブからでも引き受けられる．

```json
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:owner/repo:ref:refs/heads/main"
  }
}
```

### 認証情報の交換

パスワードは，漏れたと分かっていなくても，決めた日数のうちに交換する．
交換したパスワードは，どこか1か所(この題材ではSecrets Manager)にだけ置き，使う側はそこから読む．
複数の場所に置くと，交換するたびに古い値が残る．

## 11-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run gate:iam`は，次のどれかがあれば失敗する．
  - ポリシーを`infra/policies/`のJSONに分けず，コードの中に書いている．
  - 長期のアクセスキー(`aws_iam_access_key`)を作っている．
  - 許可のポリシーに，すべての操作(`*`，`s3:*`など)やすべての対象(`*`)を書いている．
  - GitHub Actions向けの信頼ポリシーが，`aud`と，1つのリポジトリのブランチか環境に`sub`を絞っていない．
- `mise run ops:rotate-db-password`は，データベースのパスワードを交換し，シークレットを更新する．交換した後は，新しいパスワードで接続でき，古いパスワードでは接続できない．
- `mise run ops:access-review`は，IAMの利用者とアクセスキー，CloudTrailの記録，GitHubの協力者をまとめた報告を作る．アクセスキーを持つ利用者がいれば失敗する．

### 作るもの

- `tools/gates/iam.ts`：`--infra`で調べる場所を変えられるようにする．
- `infra/policies/`のJSONと，それを読む`infra/iam.tf`．
- `tools/ops/db.ts`(シークレットから接続先を得る)，`tools/ops/rotate-db-password.ts`，`tools/ops/access-review.ts`．
- `.github/workflows/access.yml`と，運用テスト`tests/ops/access.test.ts`．

TrivyでIAMの誤りを見つけられるかを，先に試す．
試すと，`jsonencode`で書いたポリシーのワイルドカードは見つからない．

既存のテストへの影響も考える．
パスワードを交換すると，OpenTofuの出力の`database_url`はどうなるか．

## 11-4 設計書

- `ops/standards.yaml`：棚卸しの間隔と，認証情報の交換までの最長の日数を足す．
- `ops/items.yaml`：権限の絞り込み，権限の棚卸し，認証情報の交換の3つを足す．
  棚卸しと交換には，行われたことを示す問いを`records`に書く．棚卸しでは，期間中の権限の変更を監査ログで確かめる問いも書く．
- `ops/runbooks/access-review.md`と`ops/runbooks/credential-rotation.md`：棚卸しで何を確かめるか，交換の後に何をするかを書く．
- `ops/policy.md`：権限ごとに承認する人を書く．
- `.github/CODEOWNERS`：`infra/policies/`をセキュリティ責任者の承認対象にする．

## 11-5 テスト駆動の実装

### gate:iam

仕込みの状態で実行すると，次の2つが見つかる．

```text
iam.tf: 長期のアクセスキー(aws_iam_access_key)を作っている．OIDCで一時的な認証情報を使う
iam.tf: ポリシーをコードの中に書いている．policies/ のJSONに分ける
```

ポリシーをJSONに分けると，ワイルドカードと信頼ポリシーの誤りも見つかるようになる．
ヒントは次のとおりである．

- `Action`と`Resource`は，文字列か配列である．どちらでも配列として扱う関数を作る．
- 信頼ポリシーの`sub`の`${repository}`は，`templatefile`が埋める値である．ゲートでは固定の値として扱い，値そのものはOpenTofuの変数の`validation`で確かめる．

### 権限を直す

1. APIのタスクのロールは，ログの書き込み，データベースのシークレットの読み出し，エクスポートの置き場所だけを許す．
2. IAMの利用者とアクセスキーを消し，GitHub Actions向けのロールに替える．信頼ポリシーはmainのブランチに絞る．
3. `github_repository`の既定値を，自分のリポジトリに替える．

### パスワードの交換と棚卸し

1. シークレットに，接続先と認証情報をまとめてJSONで置く．OpenTofuは作るときだけ値を入れ，その後の違いは`ignore_changes`で差分から外す．
2. `tools/ops/db.ts`で，シークレットから接続先を組み立てる．`mise run dev:api`，バックアップ，運用テストも，ここから接続先を得る．
3. 交換は，今のパスワードで接続して`ALTER ROLE`で新しいパスワードを設定し，シークレットを更新する．
4. 棚卸しは，次の3つの結果をまとめる．
   - `aws iam get-credential-report`(Base64のCSV)
   - `aws cloudtrail lookup-events`
   - `gh api repos/{owner}/{repo}/collaborators`

```console
mise run up
mise run test:ops
```
