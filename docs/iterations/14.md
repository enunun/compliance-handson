# 第14回 定期報告とチェックシート

この回では，これまでの仕組みと証跡をまとめ，報告や回答で使える形にする．
毎月，運用項目ごとに，仕組みの動いた証跡の有無を確かめて報告する．
顧客から届くセキュリティチェックシートには，運用項目と証跡を示した回答の下書きを作る．

## 14-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回に仕込む問題はない．

   ```console
   mise run iteration:start 14
   ```

3. 監査人に「先月，依存関係の脆弱性検査が動いていたことを示してください」と言われたら，何を見せるか．
   ワークフローの部品の固定について，同じことを依頼されたらどうか．

## 14-2 学ぶこと

### 報告と回答

規格は次のことを求める．

- SOC 2 CC2.2，CC2.3：内部統制の状況を，組織の中と外の関係者に伝える．
- SOC 2 CC4.1：内部統制が機能しているかを，継続的に評価する．
- ISO/IEC 27001 A.5.35，A.5.36：情報セキュリティの取り組みを定期的に見直し，方針や基準を守っているかを確かめる．

仕組みを作っても，動いた証跡がなければ，動いていたことを示せない．
毎月，証跡があるかを確かめれば，欠けていることに監査の前に気づける．

### セキュリティチェックシート

SaaSを売るときには，顧客からセキュリティチェックシートが届く．
質問の多くは，ISO/IEC 27001やSOC 2の要求を言い換えたものである．
質問に規格の要求を対応づければ，同じ要求を持つ運用項目を探せる．
運用項目には，仕組み，証跡，手順書が書いてあるので，それが回答の根拠になる．

### OpenSSF Scorecard

OpenSSF Scorecardは，GitHubのリポジトリを評価し，0から10の点を付ける道具である．
観点には，ブランチ保護，actionのハッシュ固定，危ないワークフロー，署名などがある．
`ossf/scorecard-action`でワークフローから動かせる．
結果は`results_format: json`でJSONに出力でき，全体の点は`score`にある．

## 14-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run ops:report --month YYYY-MM`は，運用項目ごとに，その月の証跡を探して月次報告(`out/report-YYYY-MM.md`)を作る．
  - `records`に`match`(ログを絞る項目と値)のある問いは，CloudWatch Logsの記録を探す．
  - `gates.yml`のジョブは，証跡の保管場所の`<日付>/<コミット>/<ジョブ>/`を探す．
  - 定常の運用項目で証跡が見つからなければ「なし」，非定常の項目なら「該当なし」とする．
  - 期限を過ぎた脆弱性，30日以内に期限の来る例外，Scorecardの点もまとめる．
- `mise run ops:checksheet <YAML>`は，質問ごとに，要求が重なる運用項目を探し，回答の下書き(`out/checksheet-<名前>.md`)を作る．見つからなければ「要確認」とする．
- 運用項目の仕組みに，人が動かすmiseのタスク(`task`)を書ける．`ops:verify`はタスクがあるかを確かめる．
- `records`の`match`の項目が，ログの設計にあるかを`ops:verify`が確かめる．

### 作るもの

- `tools/ops/report.ts`と`tools/ops/checksheet.ts`，`mise.toml`の`ops:report`と`ops:checksheet`タスク．
- `checksheets/sample.yaml`：チェックシートの例．
- `.github/workflows/scorecard.yml`．
- 単体テスト`tools/ops/checksheet.test.ts`と，運用テスト`tests/ops/report.test.ts`．

運用テストでは，ほかのテストの証跡と混ざらないように，先の月(例えば2099年1月)の日付で証跡を置く．

## 14-4 設計書

- `ops/schema/items.schema.json`：仕組みに`task`を，`records`に`match`を足す．
- `ops/items.yaml`：
  - 月次報告，チェックシートへの回答，サプライチェーンの健全性の評価の3つを足す．
  - 第9回から第13回の`ops`のログの問いに，`match: { job: <作業の名前> }`を足す．
  - 期限切れのエスカレーションは，期限を過ぎたときだけ記録が残るので，`timing`を非定常にする．
- `ops/runbooks/monthly-report.md`と`ops/runbooks/checksheet.md`：報告で何を確かめるか，回答の下書きをどう見直すかを書く．
- `ops/policy.md`：報告の宛先と頻度を書く．

## 14-5 テスト駆動の実装

### 月次報告

ヒントは次のとおりである．

- 証跡の保管場所の一覧は，`aws s3api list-objects-v2 --prefix <月>-`で得る．キーの3つ目の部分がゲートの名前である．
- CloudWatch Logsの記録は，`aws logs filter-log-events`で絞れる．
  `--filter-pattern '{ $.job = "backup" }'`のように書く．`--start-time`と`--end-time`はミリ秒で指定する．
- 定常か非定常かは，運用項目の`timing`で分かる．「非定常(...)と定常(...)」のように両方を含むものは，定常として扱う．

報告を作ったら，本物の証跡で動かす．

```console
mise run up
mise run check
mise run evidence:upload
mise run ops:report
```

### 欠けた証跡を直す

報告に「なし」の運用項目があれば，その仕組みが証跡を残しているかを確かめ，直す．

### チェックシート

1. `checksheets/sample.yaml`の質問ごとに，規格の要求を書く．
2. `mise run ops:checksheet checksheets/sample.yaml`で下書きを作り，「要確認」の質問をどう答えるかを考える．

### Scorecard

1. `scorecard.yml`を作り，自分のリポジトリにpushして動かす．
2. 結果のartifactを`out/evidence/scorecard/`に置き，`mise run ops:report`に点が出ることを確かめる．
3. 点の低い項目を読み，直せるものを直す．
