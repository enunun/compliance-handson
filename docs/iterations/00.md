# 第0回 変更管理と運用項目の土台

この回では，mainに入る変更をレビューとCIで絞る仕組み(変更管理)を作る．
あわせて，この講座で毎回育てる運用項目のYAMLと，それを検証する`ops:verify`を作る．
以降の回は，すべてこの土台の上に運用項目を足していく．

ファイルの場所は，`.github/`を除き`app/`からの相対パスで示す．

## 0-1 準備

1. このリポジトリをforkするか，GitHubの「Use this template」で自分のリポジトリを作る．
2. 自分のリポジトリをcloneし，VSCodeで開いて「Reopen in Container」を実行する．
   初回は`mise run setup`が走り，道具と依存パッケージが入る．
3. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

4. 本番の環境を作り，題材のSaaSを動かす．
   `mise run up`はMiniStackの上にデータベースを作る．
   APIとWeb画面は，別々のターミナルで起動する．

   ```console
   mise run up
   mise run dev:api
   mise run dev:web
   ```

   ブラウザで<http://localhost:3000>を開き，`admin@example.com`とパスワード`password`でログインする．
   メモを追加できれば準備は終わりである．
5. この回を始める．第0回に仕込む問題はないので，何も変わらない．

   ```console
   mise run iteration:start 0
   ```

## 0-2 学ぶこと

### コントロール，仕組み，証跡

コンプライアンスの規格は，組織に「コントロール」を求める．
コントロールは，リスクを抑えるための決まりごとである．
この講座では，コントロールを次の4つに分けて考える．

| 要素 | 意味 | 変更管理の例 |
| --- | --- | --- |
| 要求 | 規格がなぜそのコントロールを求めるか | SOC 2 CC8.1は，変更を承認し，テストしてから本番に入れることを求める |
| 仕組み | 人の注意に頼らずに要求を満たす仕組み | ブランチ保護で，レビューとCIの成功がないとmainに入れないようにする |
| 証跡 | 仕組みが動いたことを示す記録 | ブランチ保護の設定と，プルリクエストのレビュー記録 |
| 例外の管理 | 仕組みを通せないときの扱い | 障害の復旧で待てないときの緊急変更の手順 |

監査では「決まりがあるか」だけでなく，「決まりどおりに動いた記録を見せられるか」を問われる．
そのため，仕組みを作るときは，証跡の置き場所も一緒に決める．

### 運用項目

運用項目は，運用で行うことを1つずつ書き出したものである．
『運用設計の教科書』では，運用項目を3つに分類する．

| 分類 | 対象 | この講座の例 |
| --- | --- | --- |
| 業務運用 | サービスの利用者に関わる運用 | 利用者の権限の管理，問い合わせの受け付け |
| 基盤運用 | システムを動かす基盤の運用 | 監視，バックアップ，パッチ |
| 運用管理 | 運用そのものを管理する運用 | 変更管理，基準の維持，定期報告 |

この講座では，運用項目を`ops/items.yaml`に書く．
各項目には，分類，要求，仕組み，証跡，タイミング，実施者を書く．
人が読む一覧(`ops/items.md`)はYAMLから生成し，手で編集しない．

基準値(承認の数，対応期限など)は`ops/standards.yaml`に分けて書く．
基準値は方針の決定なので，運用項目とは承認する人が違う．
この違いは，GitHubのCODEOWNERSで表す．

### JSON Schema

JSON Schemaは，JSONやYAMLのデータの形を定める書式である．
例えば，次のスキーマは「`count`は1以上の整数で，必ずある」ことを表す．

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["count"],
  "properties": {
    "count": { "type": "integer", "minimum": 1 }
  }
}
```

YAMLの先頭に`# yaml-language-server: $schema=./schema/xxx.schema.json`と書くと，VSCodeのYAML拡張機能が補完と検証をしてくれる．
`tools/ops/verify.ts`では，Ajvというライブラリでスキーマを検証する．

```ts
import { Ajv2020 } from "ajv/dist/2020.js";

const ajv = new Ajv2020({ allErrors: true });
if (!ajv.validate(schema, data)) {
  console.log(ajv.errors); // instancePath(どこが)とmessage(何が)を持つ
}
```

### ゲートのテスト

ゲートは，だめな入力を見つけたら失敗(終了コードが0以外)して，変更を止める仕組みである．
ゲートが正しく動くかは，入力を用意して確かめる．

- だめな入力(fixture)を与えると，失敗して理由を表示する．
- 正しい入力を与えると，成功する．

この講座では，ゲートのテストを`tests/gates/`に置き，入力を`tests/gates/fixtures/`に置く．
`tests/gates/helpers.ts`の`run`はコマンドを実行して終了コードと出力を返し，`fixture`は入力の場所を返す．

### act

actは，GitHub Actionsのワークフローを手元のDockerで実行する道具である．
pushする前に，ワークフローの書き方の誤りを見つけられる．
`mise run ci`は，リポジトリ直下でactを実行する．

## 0-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`(`app/`の直下)に書く．
ゲートのテストと単体テストを分けて書く．

### 要求

- 基準値と運用項目がスキーマに合わなければ，`mise run ops:verify`が失敗し，どのファイルのどこが合わないかを表示する．
- 運用項目の仕組みに書いたワークフローやジョブがなければ，`mise run ops:verify`が失敗する．
- 運用項目に書いた手順書のファイルがなければ，`mise run ops:verify`が失敗する．
- 運用項目一覧(`ops/items.md`)が`ops/items.yaml`と合わなければ，`mise run ops:verify`が失敗し，作り直す方法を表示する．
- `mise run ops:render`は，`ops/items.yaml`から運用項目一覧を作る．
- `mise run check`は，ゲートのテストと`ops:verify`も実行する．
- mainへの変更には，レビューの承認とCIの`check`ジョブの成功が要る．

### 使用例

```console
$ mise run ops:verify
ops: ok
$ mise run ops:render
wrote ops/items.md
```

### 作るもの

- `tools/ops/verify.ts`の`verify(options: VerifyOptions): Problem[]`と，コマンドとして実行したときの処理．
  `--ops`，`--workflows`，`--schema`で場所を変えられるようにする．
- `tools/ops/render.ts`の次の2つの関数．
  `render(items: ItemsFile): string`と`renderedPath(opsDir: string): string`である．
- `.github/workflows/ci.yml`と`.github/CODEOWNERS`．

ゲートのテストの入力には，正しい運用項目と，それぞれの要求に反する運用項目を用意する．

## 0-4 設計書

この講座の設計書は，運用項目と基準のYAML，手順書，運用方針の3つである．
この回で，すべての初版を書く．

- `ops/schema/standards.schema.json`と`ops/schema/items.schema.json`：0-3の要求から，必須の項目と値の範囲を決める．
  分類は3つの値のどれか，実施者は「自動」か「人」に限る．
- `ops/standards.yaml`：変更管理の基準値を書く．mainへの変更に要る承認の数である．
- `ops/items.yaml`：最初の運用項目として`change-management`を書く．
  仕組みは，この後で作る`ci.yml`の`check`ジョブである．
  要求には，SOC 2 CC8.1とISO/IEC 27001 A.8.32を書く．
- `ops/runbooks/emergency-change.md`：レビューを待てないときの緊急変更の手順を書く．
  誰が実施できるか，何を記録するか，事後に誰が確認するかを含める．
- `ops/policy.md`：見出しのコメントに従って，体制と役割，変更の流れを書く．

## 0-5 テスト駆動の実装

テストリストの項目を1つずつ，失敗するテストを書いてから実装する．
ゲートのテストは次のコマンドで実行する．

```console
mise run test:gates
```

### ops:verify

`verify.ts`は，まだ中身がない．
最初のゲートのテストを書いて実行すると，何も出力されずに失敗する．

```text
 ❯ |gates| tests/gates/ops-verify.test.ts (4 tests | 4 failed) 803ms
   ❯ ops:verify (4)
     × 正しい運用項目では通る 267ms
...
AssertionError: expected '' to contain 'ops: ok'
```

ヒントは次のとおりである．

- YAMLは`tools/ops/items.ts`の`readYaml`で読める．
- ワークフローのジョブは，YAMLの`jobs`の下のキーである．
- コマンドとして実行されたかどうかは`import.meta.main`で分かる．引数は`node:util`の`parseArgs`で読む．
- 問題が1つでもあれば，すべて表示してから`process.exit(1)`で終える．

### ops:render

`render`の単体テストは`tools/ops/render.test.ts`に書く．
単体テストは`mise run test`で実行する．
表の1行が1つの運用項目になる．
生成したファイルの先頭に，手で編集しないことを書いておく．

`ops:verify`は，`render`の結果と`ops/items.md`を比べて，古い一覧を検出する．

### 検証のコマンドに組み込む

`mise.toml`の`check`タスクの`depends`に，`test:gates`と`ops:verify`を足す．
これで，手元の`mise run check`とCIが，同じゲートを実行する．

### CIとブランチ保護

1. `.github/workflows/ci.yml`に，`app/`で`mise run check`を実行する`check`ジョブを書く．
   道具は`jdx/mise-action`で入れる．
2. `mise run ci`で，actを使ってワークフローを手元で実行し，成功することを確かめる．
3. `.github/CODEOWNERS`に，`app/ops/standards.yaml`の承認者を書く．
4. GitHubにpushし，Actionsで`check`が成功することを確かめる．
5. GitHubのSettingsのBranchesで，mainにブランチ保護を設定する．
   プルリクエストを必須にし，承認の数を基準値と同じにし，`check`を必須のチェックにする．
   CODEOWNERSのレビューも必須にする．

### 証跡

ブランチ保護の設定は，GitHubのAPIで取得できる．
`gh`を使うには，先に`gh auth login`でログインしておく．

```console
gh api "repos/{owner}/{repo}/branches/main/protection"
```

この結果を`out/evidence/change/`に日付つきで保存する`ops:evidence:change`タスクを，`mise.toml`に作る．

## 0-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．抜けていた項目はあるか．
2. ゲートのテストで，失敗することだけでなく，失敗の理由の表示まで確かめるのはなぜか．
3. 基準値と運用項目を別のファイルに分けた理由を，CODEOWNERSと結び付けて説明する．
4. ブランチ保護の設定がGitHubの画面だけにあると，監査でどんな問題が起きるか．
5. 運用項目のYAMLと実装を比べ，合わないところがあれば直す．

## 0-7 発展課題

`.github/CODEOWNERS`に`app/ops/standards.yaml`の行がなければ失敗する検査を，`ops:verify`に足す．
テストリスト，設計書，実装の順に進める．
