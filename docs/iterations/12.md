# 第12回 脆弱性のトリアージ

この回では，見つかった脆弱性に影響があるかを判断し，直すまでの期限を管理する仕組みを作る．
影響がないものは，その根拠をOpenVEXの文書で示す．
期限を過ぎたものは，第7回のAlertmanagerで上位者に知らせる．

## 12-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回の問題を当て，コミットする．

   ```console
   mise run iteration:start 12
   git add -A
   git commit -m "ログインした端末のアドレスをAPIへ渡す"
   ```

3. `ops/exceptions.yaml`の`EXC-004`を読む．
   この例外は，いつ見つかった脆弱性のものか．例外の期限まで，脆弱性を残してよいか．

## 12-2 学ぶこと

### トリアージ

規格は次のことを求める．

- ISO/IEC 27001 A.8.8：技術的な脆弱性の影響を評価し，適時に対処する．
- SOC 2 CC7.4：見つかった問題に，決めた手順で対応する．

見つかった脆弱性には，次の順で対応する．この判断をトリアージという．

1. 直した版があれば，更新する．
2. 直せなければ，自分たちのシステムに影響があるかを調べる．脆弱な関数を呼んでいなければ，影響はない．
3. 影響があれば，決めた期限までに直す．期限は重大度ごとに決め，見つかった日から数える．この期限をSLA(Service Level Agreement)と呼ぶことが多い．

第2回の例外には，期限はあっても，その長さを決める基準がない．
見つかった日も残らないので，いつまでに直すべきかが分からない．

### VEX

VEX(Vulnerability Exploitability eXchange)は，ある製品がある脆弱性の影響を受けるかを伝える文書である．
OpenVEXはその形式の1つで，JSONで書く．

```json
{
  "@context": "https://openvex.dev/ns/v0.2.0",
  "@id": "urn:example:vex:1",
  "author": "example",
  "timestamp": "2026-10-04T00:00:00Z",
  "version": 1,
  "statements": [
    {
      "vulnerability": { "name": "CVE-2024-29415" },
      "products": [{ "@id": "pkg:npm/ip" }],
      "status": "not_affected",
      "justification": "vulnerable_code_not_in_execute_path"
    }
  ]
}
```

- `status`：影響の状態．`not_affected`(影響なし)，`affected`(影響あり)，`fixed`(直した)，`under_investigation`(調査中)の4つである．
- `justification`：`not_affected`の根拠．`vulnerable_code_not_in_execute_path`(脆弱な処理を通らない)など5つから選ぶ．
- `products`：対象をpURL(Package URL)で書く．`pkg:npm/ip`はnpmの`ip`パッケージを表す．

Trivyは`--vex`でOpenVEXの文書を読み，`not_affected`の脆弱性を結果から外す．
SBOMと同じく，VEXの文書は顧客に渡して「この脆弱性の影響はない」と示すのにも使える．

### エスカレーション

期限を過ぎたことは，担当者だけでなく，判断できる人(上位者)に知らせる．
これをエスカレーションという．
AlertmanagerのAPI(`POST /api/v2/alerts`)は，Prometheusを通さずにアラートを受け付ける．
第7回の振り分け(`severity`のラベル)が，そのまま使える．

```console
curl -X POST http://alertmanager:9093/api/v2/alerts -H 'Content-Type: application/json' \
  -d '[{"labels": {"alertname": "Test", "severity": "page"}}]'
```

## 12-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- 脆弱性の例外(`target`が`CVE-`か`GHSA-`で始まる)には，トリアージの結果を書く．
  書くのは，pURL，重大度，見つかった日，状態(`affected`か`not_affected`)である．`not_affected`には根拠も書く．
  書いていなければ，`mise run ops:verify`を失敗させる．
- `mise run gate:sla`は，`affected`の例外が，見つかった日から基準値の日数を過ぎていれば失敗する．例外の期限がその日数を超えていても失敗する．
- `gate:sla`は，Alertmanagerの場所(`ALERTMANAGER_URL`)があれば，期限を過ぎたものを`severity: page`のアラートとして送り，運用の作業の記録を残す．
- `gate:sca`と`gate:image`は，`not_affected`の例外をOpenVEXの文書にしてTrivyに渡し，証跡に残す．

### 作るもの

- `tools/gates/sla.ts`：`--exceptions`，`--today`，`--alertmanager`で入力を変えられるようにする．
- `tools/gates/trivy.ts`の`toOpenVex`．
- `mise.toml`の`gate:sla`タスク，`ci.yml`の`sla`ジョブ，`rescan.yml`の`gate:sla`のステップ．
- 運用テスト`tests/ops/escalation.test.ts`．

既存のテストへの影響も考える．
第2回の`gate:sca`のテストの例外は，どちらの形で外すことになるか．

## 12-4 設計書

- `ops/standards.yaml`：重大度ごとの直すまでの日数(`vulnerability.sla_days`)を足す．
- `ops/schema/exceptions.schema.json`：トリアージの結果の4つの項目を足す．脆弱性の例外で必須にするには，JSON Schemaの`if`と`then`を使う．
- `ops/items.yaml`：脆弱性のトリアージと期限の管理，期限切れのエスカレーションの2つを足す．
  エスカレーションには，いつ上位者に知らせたかを示す問いを`records`に書く．
- `ops/runbooks/vulnerability-triage.md`：影響があるかの判断の仕方と，期限を過ぎたときにすることを書く．
- `ops/policy.md`：期限を過ぎたときの連絡の経路(誰に，いつ)を書く．

## 12-5 テスト駆動の実装

### トリアージの結果を書く

スキーマを直して`mise run ops:verify`を実行すると，`EXC-004`のトリアージの結果がないと分かる．

```text
ops/exceptions.yaml: /exceptions/2 must have required property 'severity'
ops/exceptions.yaml: /exceptions/2 must have required property 'found'
ops/exceptions.yaml: /exceptions/2 must have required property 'status'
ops/exceptions.yaml: /exceptions/2/package must match pattern "^pkg:"
```

まず，コメントにある見つかった日と重大度を移し，状態を`affected`として書く．

### gate:sla

`gate:sla`を作って実行すると，期限を過ぎていることが分かる．

```text
EXC-004: CVE-2024-29415(HIGH)は直す期限(2026-09-19)を過ぎている
```

ヒントは次のとおりである．

- 期限は，`found`に`sla_days`の重大度の日数を足した日である．日付は`YYYY-MM-DD`の文字列で比べられる．
- SASTの例外のように，状態のない例外は対象にしない．

### トリアージする

`ip`の直した版は，まだ出ていない．
影響があるかを調べ，結果を`EXC-004`に書く．

1. 脆弱性の説明を読み，どの関数に問題があるかを確かめる．

   ```console
   trivy fs --scanners vuln --format json . | jq '.Results[].Vulnerabilities[]? | select(.VulnerabilityID == "CVE-2024-29415") | .Description' | sort -u
   ```

2. 題材がその関数を呼んでいるかを，コードを検索して確かめる．
3. 影響がなければ，状態を`not_affected`にして根拠を書く．影響があれば，期限までに`ip`を使わない形に直す．

### OpenVEXへのリファクタリング

`toTrivyIgnore`から`not_affected`の例外を外し，`toOpenVex`で作った文書を`--vex`で渡す．
`trivy config`は`--vex`を受け付けないので，設定の検査には渡さない．

### 期限切れを知らせる

1. `gate:sla`に，期限を過ぎたものをAlertmanagerへ送る処理を足す．送ったら，第9回の`opsLog`で`escalation`の記録を残す．
2. 運用テストを書いて確かめる．Alertmanagerの`GET /api/v2/alerts`の結果の`receivers`で，どの通知先に振り分けられたかが分かる．

```console
mise run up
mise run test:ops
```

## 12-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．
2. `not_affected`と判断した後も，`ip`を使わない形に直すべきか．直すなら，いつ直すか．
3. 期限を過ぎたら上位者に知らせるのは，なぜか．担当者に知らせ続けるだけでは，何が起きるか．
4. 見つかった日を人が例外に書く今の仕組みには，どんな弱さがあるか．
5. 運用項目と実装を比べ，合わないところがあれば直す．

## 12-7 発展課題

`gate:sla`に，例外のない脆弱性(まだトリアージしていないもの)の扱いを足す．
`rescan.yml`の結果のうち，例外にないものを`severity: ticket`のアラートとして開発チームに知らせ，トリアージを促す．
テストリスト，設計書，実装の順に進める．
