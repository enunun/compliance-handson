# 第5回 コンテナとIaCの設定検査

この回では，コンテナイメージと，DockerfileやOpenTofuのコードの設定を検査するゲートを作る．
コードに脆弱性がなくても，動かす環境の設定を誤れば，データが漏れたり乗っ取られたりする．

## 5-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回の問題を当て，コミットする．

   ```console
   mise run iteration:start 5
   git add -A
   git commit -m "APIをコンテナにし，エクスポートの置き場所を作る"
   ```

3. APIのイメージを作って動かしてみる．

   ```console
   docker build -t app-api:local apps/api
   ```

4. `apps/api/Dockerfile`と`infra/exports.tf`を読み，誰の権限で動き，誰が読めるかを考える．

## 5-2 学ぶこと

### 設定の誤り

クラウドの事故の多くは，コードの脆弱性ではなく設定の誤りから起きる．
例えば，バケットを誤って公開すると，誰でも中身を読める．
コンテナをrootで動かすと，コンテナを乗っ取られたときの被害が大きくなる．

規格は次のことを求める．

- ISO/IEC 27001 A.8.9：ハードウェア，ソフトウェア，サービス，ネットワークの設定を決め，記録し，監視する．

設定をコード(Dockerfile，OpenTofu)で書いていれば，デプロイの前に検査できる．

### Trivyでの設定とイメージの検査

`trivy config`は，DockerfileやOpenTofuのコードを読み，よく知られた設定の誤りを見つける．
誤りごとに識別子(例えば`DS-0002`，`AWS-0087`)と重大度がある．

```console
trivy config --severity HIGH,CRITICAL infra
```

`trivy image`は，コンテナイメージに入っているOSのパッケージと，アプリの依存関係の脆弱性を調べる．
OSのサポートが終わっていると警告を出すが，それだけでは失敗にしない．
結果のJSONの`Metadata.OS.EOSL`が`true`なら，サポートが終わっている．

### コンテナを安全にする

- ベースイメージ：distroless(`gcr.io/distroless/static-debian12`など)は，シェルやパッケージ管理を持たない最小のイメージである．
  入っているものが少ないほど，脆弱性も少ない．Goのように1つのバイナリで動くプログラムに向く．
- 利用者：`USER`命令で，rootではない利用者を指定する．distrolessの`nonroot`のイメージでは，UIDが65532の利用者を使える．

### S3のバケットを守る

- パブリックアクセスのブロック(`aws_s3_bucket_public_access_block`)：誤って公開のポリシーやACLを付けても，公開されないようにする．
- 暗号化(`aws_s3_bucket_server_side_encryption_configuration`)：自分たちで管理する鍵(KMSの鍵)で暗号化すると，鍵の利用を記録し，鍵の交換を決められる．

データを外部に共有したいときは，バケットを公開せず，期限つきの署名つきURLを発行する．

## 5-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run gate:config`は，DockerfileとOpenTofuのコードに，基準値の重大度以上の設定の誤りがあれば失敗する．
  例外に載った誤りは，期限まで外す．
- `mise run gate:image`は，APIのイメージを作り，基準値の重大度以上の脆弱性があるか，サポートの終わったOSを使っていれば失敗する．
- どちらも，結果をJSONで`out/evidence/`に残す．

### 作るもの

- `tools/gates/config.ts`：`--target`と`--exceptions`で入力を変えられるようにする．
- `tools/gates/image.ts`：`--image`(調べるイメージ)と`--exceptions`で入力を変えられるようにする．
- `mise.toml`の`image:build`，`gate:image`，`gate:config`タスク．
  `image:build`は，環境に合わせたビルドの引数を`DOCKER_BUILD_ARGS`で足せるようにする．

ゲートのテストの入力には，rootで動くDockerfile，公開のバケット，直した設定を用意する．
イメージの検査のテストでは，サポートの終わったOSの公開イメージ(例えば`alpine:3.20`)と，サポート中のdistrolessのイメージを使う．

`gate:sca`とTrivyの呼び出しが重なる．
共通の処理をどこに置くかも考える．

## 5-4 設計書

`ops/items.yaml`に，コンテナイメージの検査と，DockerfileとOpenTofuの設定の検査の2つを足す．

## 5-5 テスト駆動の実装

### gate:config

題材に対して実行すると，仕込んだバケットだけでなく，これまでの回で作ったバケットとデータベースの誤りも見つかる．
次は出力の一部である．

```text
apps/api/Dockerfile (dockerfile)
Tests: 1 (SUCCESSES: 0, FAILURES: 1)
Failures: 1 (UNKNOWN: 0, LOW: 0, MEDIUM: 0, HIGH: 1, CRITICAL: 0)
DS-0002 (HIGH): Specify at least 1 USER command in Dockerfile with non-root user as argument
...
infra/database.tf (terraform)
...
AWS-0080 (HIGH): Instance does not have storage encryption enabled.
...
infra/exports.tf (terraform)
Tests: 5 (SUCCESSES: 0, FAILURES: 5)
Failures: 5 (UNKNOWN: 0, LOW: 0, MEDIUM: 0, HIGH: 5, CRITICAL: 0)
AWS-0086 (HIGH): No public access block so not blocking public acls

AWS-0091 (HIGH): No public access block so not blocking public acls
AWS-0093 (HIGH): No public access block so not restricting public buckets
AWS-0132 (HIGH): Bucket does not encrypt data with a customer managed key.
```

ヒントは次のとおりである．

- `.trivyignore.yaml`の形では，設定の誤りの除外を`misconfigurations`に書く．
- `.terraform/`には，取得したプロバイダが入っている．検査の対象から外す．

### gate:image

`trivy image`の結果のJSONを読み，OSのサポートを確かめる．
仕込みのイメージでは次のように失敗する．

```text
app-api:local: alpine 3.20.10 はサポートが終わっている
```

### 誤りへの対応

1. Dockerfileの実行の段階を，distrolessの`nonroot`のイメージに替え，`USER`を書く．
2. `infra/kms.tf`に鍵を作り，2つのバケットにパブリックアクセスのブロックと暗号化を足す．
3. エクスポートのバケットの公開のポリシーを外す．
4. データベースに`storage_encrypted = true`を足す．
5. 本番の環境に適用し，運用テストが通ることを確かめる．

   ```console
   tofu -chdir=infra plan
   mise run up
   mise run test:ops
   ```

### CI

`ci.yml`に`image`ジョブと`config`ジョブを足し，結果をartifactに残す．
`evidence`ジョブの`needs`にも足す．
