# 第10回 更新と定期的な再検査

この回では，部品を新しく保ち続ける仕組みを作る．
依存関係の更新を自動でプルリクエストにし，リリース済みのイメージを毎日検査し直し，サポートの終わりが近いランタイムやベースイメージを止める．
第2回で受け入れた例外も，この回の更新で閉じる．

## 10-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回の問題を当て，コミットする．

   ```console
   mise run iteration:start 10
   git add -A
   git commit -m "ビルドのイメージを替える"
   ```

3. `apps/api/Dockerfile`のビルド用のイメージの版を見る．その版のGoは，いつまでサポートされるか．

## 10-2 学ぶこと

### 一度通したゲートの外で起きること

第2回のゲートは，変更のたびに依存関係を検査する．
しかし，変更がなくても，次のことは起きる．

- 使っている版に，新しい脆弱性が公開される．
- 使っている言語やOSのサポートが終わり，修正が出なくなる．

これに気づくには，変更とは関係なく定期的に検査し，更新を続ける仕組みが要る．

規格は次のことを求める．

- ISO/IEC 27001 A.8.8：技術的な脆弱性の情報を適時に得て，対処する．
- ISO/IEC 27001 A.8.19：運用中のシステムのソフトウェアの導入を管理する．

### Renovate

Renovateは，依存関係の新しい版を見つけて，更新のプルリクエストを作るGitHubのアプリである．
pnpm，Goのモジュール，Dockerfileのイメージ，`mise.toml`，GitHub Actionsのactionを更新できる．
設定はリポジトリ直下の`renovate.json`に書く．

- `extends`：よく使う設定の組．`helpers:pinGitHubActionDigests`は，actionをハッシュで固定し，ハッシュとコメントの版を一緒に更新する．
- `schedule`：プルリクエストを作る時間帯．
- `minimumReleaseAge`：公開からこの期間がたった版だけを使う．公開直後に問題が見つかる版を避けられる．
- `vulnerabilityAlerts`：脆弱性の修正の扱い．スケジュールを待たずに出せる．

### サポートの終了

言語やOSには，サポートの期間がある．
endoflife.dateは，製品ごとのサポートの終了日をAPIで公開している．

```console
curl https://endoflife.date/api/v1/products/go/
```

結果の`result.releases`に，版(`name`)ごとの`isEol`(終わったか)と`eolFrom`(終わる日)がある．
Goのように，次の版が出るまで終了日が決まらない製品もある．

## 10-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run gate:eol`は，`mise.toml`の言語のランタイム(Node.js，Go)と，Dockerfileのベースイメージ(`node`，`golang`)の版を調べる．
  サポートが終わっているもの，基準値の日数のうちに終わるものがあれば失敗する．
- サポートの情報が見つからない版も失敗にする．
- リリース済みのイメージを，毎日，最新の脆弱性のデータで検査し直し，結果を残す．
- Renovateが，依存関係の更新を毎週まとめてプルリクエストにする．脆弱性の修正はすぐに出す．

### 作るもの

- `tools/gates/eol.ts`：`--mise`，`--dockerfile`(複数)，`--data`(endoflife.dateのデータの代わりに使うJSONの場所)，`--today`で入力を変えられるようにする．
- `mise.toml`の`gate:eol`と`rescan:image`タスク，`ci.yml`の`eol`ジョブ．
- `.github/workflows/rescan.yml`とリポジトリ直下の`renovate.json`．

ゲートのテストでは，endoflife.dateの代わりに，日付を決めたJSONを`--data`で渡す．
`mise.toml`を読むには，TOMLのパーサー(`smol-toml`)を使う．

## 10-4 設計書

- `ops/standards.yaml`：サポートの終了までの日数の基準を足す．
- `ops/items.yaml`：依存関係の更新，リリース済みのイメージの再検査，サポートの終了の管理の3つを足す．
  依存関係の更新の仕組みは，ワークフローではなくRenovateが読む`renovate.json`である．
  運用項目のスキーマの仕組みに，設定ファイル(`file`)を足し，`ops:verify`でファイルがあるかを確かめる．
- `ops/policy.md`：更新を取り込む方針を書く．いつ，どの版を，どう確かめて取り込むか．

## 10-5 テスト駆動の実装

### gate:eol

題材に対して実行すると，仕込まれたイメージが見つかる．

```text
apps/api/Dockerfile: golang:1.25: go 1.25 はサポートが終わっている(2026-08-19)
```

ヒントは次のとおりである．

- Dockerfileの`FROM`の行から，イメージの名前とタグの先頭の版を取り出す．`golang:1.26-alpine`なら`1.26`である．
- `mise.toml`の版`24.21.0`は，endoflife.dateの版`24`に当たる．版の名前と一致するか，版の名前に`.`を付けたもので始まるかで探す．
- endoflife.dateへの問い合わせは`fetch`で行う．`--data`があれば，代わりにファイルを読む．

直したら，ビルド用のイメージをサポート中の版に戻す．

### 例外を閉じる

第2回で例外にしたgolang-jwtの脆弱性は，4.5.2で直っている．
版を上げ，例外の一覧から`EXC-001`を消す．
`mise run gate:sca`が，例外なしで通ることを確かめる．

```console
go -C apps/api get github.com/golang-jwt/jwt/v4@v4.5.2
```

### 再検査とRenovate

1. `rescan.yml`は，最新の`v`で始まるタグのイメージを決め，`trivy registry login`でGHCRにログインする．
   そのうえで，`mise run rescan:image`で検査する．
   リリースがまだなければ何もしない．
2. `renovate.json`を書く．書いた設定は，RenovateのJSON Schemaで確かめられる．
3. GitHubで，Renovateのアプリをリポジトリに入れる．最初に設定の確認のプルリクエスト(Configure Renovate)が来る．

## 10-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．
2. ゲートのテストで，endoflife.dateに問い合わせず，ファイルのデータを使うのはなぜか．
3. `minimumReleaseAge`で新しい版をすぐに使わないことには，どんな利点と欠点があるか．
4. 再検査で新しい脆弱性が見つかったとき，誰がいつまでに何をするかは，まだ決まっていない．第12回でこれを決める．今の仕組みでは，誰が気づくか．
5. 運用項目と実装を比べ，合わないところがあれば直す．
