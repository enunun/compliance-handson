# 第6回 ワークフローと成果物の完全性

この回では，CIが使う部品(action)のすり替えを防ぐ仕組みと，出荷するイメージに署名とprovenance(どこでどう作ったかの記録)を付ける仕組みを作る．
actionはロックファイルで固定し，CIはロックファイルに記録したコミットだけを動かす．
受け取る側は，イメージがこのリポジトリのCIで作られたことを検証できるようになる．

## 6-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回に仕込む問題はない．問題はすでに`ci.yml`にある．

   ```console
   mise run iteration:start 6
   ```

3. `.github/workflows/ci.yml`の`uses:`の行を読み，それぞれが何を指しているかを考える．
   使っているactionが，さらに別のactionを使っていたら，何を固定すれば足りるかも考える．

## 6-2 学ぶこと

### サプライチェーンの攻撃

ソフトウェアは，依存関係やCIの部品など，多くの他人の成果物を使って作られる．
その途中のどこかをすり替えられると，自分たちのコードに問題がなくても，悪意のあるものを出荷してしまう．
例えば，CIで使うactionのタグを，攻撃者が悪意のあるコミットに付け替えると，次のCIの実行でそれが動く．
2025年3月には，広く使われていた`tj-actions/changed-files`のタグが付け替えられ，多くのリポジトリのCIでシークレットがログに出た．

規格や枠組みは次のことを求める．

- SLSA(Supply-chain Levels for Software Artifacts)：成果物がどのソースからどのビルドで作られたかを，検証できる形で記録する．
- NIST SSDF PS.2：リリースするソフトウェアの完全性を確かめる仕組みを提供する．

### actionをロックファイルで固定する

`uses: actions/checkout@v5`のタグやブランチは，後から別のコミットを指すように変えられる．
これまでは，`uses:`に40桁のコミットのハッシュを書いて固定していた．
2026年10月に，GitHub Actionsのワークフローのロックファイルが一般提供になった．
`uses:`にはタグを書いたまま，実際に動くコミットをロックファイル(`.github/workflows/actions.lock`)に記録する．

```yaml
# ワークフロー：読みやすいタグのまま書く
- uses: actions/checkout@v5.1.0
```

```yaml
# .github/workflows/actions.lock：gh actions-lock が作る．手で編集しない
version: 'v0.0.3'
workflows:
    '.github/workflows/ci.yml':
        - 'actions/checkout@v5.1.0'
dependencies:
    'actions/checkout@v5.1.0':
        ref: 'v5.1.0'
        commit: 'sha1-fbc6f3992d24b796d5a048ff273f7fcc4a7b6c09'
        owner_id: 44036562
        repo_id: 197814629
```

ロックファイルに載ったワークフロー(オンボードしたワークフロー)では，GitHub Actionsは次のように動く．

- ワークフローが使うすべてのactionが，ロックファイルに載っていなければならない．載っていないactionのステップは失敗する．
- タグが別のコミットに付け替えられても，記録したコミットを動かす．
- 記録したコミットが，記録したタグかブランチから辿れなければ動かさない．フォークにしかないコミットにすり替えることはできない．

`uses:`にハッシュを書く方法と比べて，次の利点がある．

- actionが中で使うaction(推移的な依存)も固定できる．ハッシュを書く方法では，自分のワークフローの`uses:`しか固定できない．
- リポジトリの番号(`owner_id`と`repo_id`)を記録する．リポジトリが消されて同じ名前で作り直されても，別物だと分かる．
- ワークフローが読みやすく，版の更新の差分(ロックファイルの`commit`)をレビューしやすい．

ロックファイルは，GitHub CLIの拡張`gh actions-lock`で作る．

```console
gh extension install github/gh-actions-lock --pin v0.4.0
gh actions-lock            # ロックファイルを作り直す．v5 のようなタグは v5.1.0 に絞る
gh actions-lock --verify   # 書き換えずに，ロックファイルが最新で，記録したコミットが今も元のタグから辿れるかを確かめる(CI向け)
```

`gh actions-lock`は1.0より前の版で，版ごとに動作やロックファイルの形式が変わりうる．
版を`--pin`で固定し，上げるときは差分を確かめる．

ロックファイルが固定しないものもある．

- ジョブの`uses:`で呼ぶ，別のリポジトリのreusable workflow．40桁のコミットのハッシュで固定する．
- コンテナのイメージ(`docker://`)．ダイジェスト(`@sha256:...`)で固定する．
- 同じリポジトリの中の参照(`./`)．そのコミットの中身がそのまま動く．

GitHubには，ロックファイルのないワークフローの実行を止めるポリシー(Require lockfile)もある．
組織やEnterpriseでは，管理者がまとめて設定できる．

ロックファイルは，actionが安全かどうかは決めない．
ロックファイルの変更は，動くコードの変更としてレビューする．

使うactionを減らすことも，すり替えられる場所を減らす．
miseで入れた道具をコマンドで使えば，それをするためのactionは要らない．

### キーレスの署名

Sigstoreのcosignは，コンテナイメージに署名する．
キーレスの署名では，秘密鍵を保管しない．
GitHub ActionsのOIDCのトークンで「このリポジトリのこのワークフローが署名した」という短い期間の証明書を受け取り，それで署名する．
署名は公開の記録(透明性ログ)にも残る．

```console
cosign sign --yes ghcr.io/owner/repo/api@sha256:...
cosign verify \
  --certificate-identity-regexp '^https://github.com/owner/repo/\.github/workflows/release\.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/owner/repo/api@sha256:...
```

ワークフローでOIDCのトークンを使うには，`permissions`に`id-token: write`を書く．

### provenance

provenanceは，成果物を「どのリポジトリの，どのコミットから，どのワークフローで作ったか」の記録である．
`actions/attest-build-provenance`は，SLSAの形式のprovenanceを作り，GitHubとレジストリに保存する．
`gh attestation verify`で検証できる．

イメージはタグではなくダイジェスト(`@sha256:...`)で指定する．
タグは付け替えられるが，ダイジェストは中身から決まるからである．

## 6-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run gate:pinning`は，次のものがあれば失敗する．ファイルと参照を表示する．
  - ロックファイルに載っていないワークフロー．
  - ステップの`uses:`のうち，そのワークフローの分としてロックファイルに載っていないaction．
  - ジョブの`uses:`(reusable workflow)のうち，コミットのハッシュで固定されていない参照．
  - ダイジェストで固定されていない`docker://`のイメージ．
- 同じリポジトリの中の参照(`./`で始まる)は対象にしない．
- CIは，`gh actions-lock --verify`で，ロックファイルが最新で，記録したコミットが今も元のタグから辿れることも確かめる．
- `v`で始まるタグをpushすると，イメージをGHCRに置き，署名とprovenanceを付け，検証の結果を証跡に残す．

### 作るもの

- `.github/workflows/actions.lock`：`mise run actions:lock`で作る．
- `tools/gates/pinning.ts`：`--workflows`でワークフローの場所を変えられるようにする．ロックファイルは，その場所の`actions.lock`を読む．
- `.github/workflows/release.yml`．
- `tools/gates/verify-image.sh`：`<イメージ>@<ダイジェスト>`を受け取り，署名とprovenanceを検証して結果を`out/evidence/release/`に残す．
- `mise.toml`の`gate:pinning`，`actions:lock`，`actions:verify`，`release:verify`タスク．
  `gh actions-lock`の版は，拡張を入れるタスク(`actions:setup`)で固定する．

## 6-4 設計書

- `ops/items.yaml`：ワークフローの部品の固定と，成果物の署名とprovenanceの2つを足す．
  部品の固定の仕組みは`ci.yml`の`pinning`ジョブ，署名の仕組みは`release.yml`の`release`ジョブである．
- `ops/runbooks/actions-lock.md`：actionを足したり版を上げたりする手順を書く．
  ロックファイルの差分のどこをレビューするかも書く．
- `ops/runbooks/verify-image.md`：イメージの署名とprovenanceを確かめる手順を書く．
  検証に失敗したら何をするかも書く．

## 6-5 テスト駆動の実装

### gate:pinning

ゲートのテストの入力は，ワークフローとロックファイルの組で用意する．
ロックファイルは手で書いてよい．fixtureの中の`actions.lock`は，GitHub Actionsが読むことはない．

題材に対して実行すると，ロックファイルがまだないので，すべてのワークフローが見つかる．

```text
ci.yml: ロックファイルに載っていない
actionは mise run actions:lock でロックファイルに固定する．
```

`gh actions-lock`は，GitHubのAPIを使う．先に`gh auth login`でログインしておく．
ロックファイルを作り，ワークフローとロックファイルの差分を確かめる．

```console
mise run actions:lock
git diff
```

`uses:`のタグは，`v5`から`v5.1.0`のように，そのとき指していた版に絞られる．
ロックファイルには，各タグのコミットとリポジトリの番号が入る．
もう一度`mise run gate:pinning`を実行し，通ることを確かめる．
`mise run ci`でワークフローが動くことも確かめる．actはロックファイルを読まず，タグのまま動かす．

### release.yml

1. `permissions`に，`packages: write`，`id-token: write`，`attestations: write`を書く．
   ワークフロー全体の`permissions`は`contents: read`に絞り，`release`ジョブだけで広げる．
2. GHCRへのログインは，`docker login`に`GITHUB_TOKEN`を渡す．
3. イメージを作ってpushし，`docker inspect`でダイジェストを得る．
   GHCRのイメージの名前は小文字にする．
4. `cosign sign`で署名し，`actions/attest-build-provenance`でprovenanceを付ける．
5. `mise run release:verify`で検証し，`out/evidence/`をartifactに残す．
6. ワークフローを足したので，`mise run actions:lock`でロックファイルを作り直す．
   `actions/attest-build-provenance`が中で使う`actions/attest`も，ロックファイルに載ることを確かめる．

### GitHubで確かめる

OIDCのトークンと`gh actions-lock --verify`はactでは動かないので，この回はGitHubで確かめる．
`pinning`ジョブが通ることを確かめてから，タグをpushする．

```console
git tag v0.1.0
git push origin v0.1.0
```

Actionsで`release`が成功したら，手順書のとおりに手元でも検証する．

リポジトリのSettingsのActionsに，ロックファイルを必須にするポリシー(Require lockfile)があれば，有効にしてみる．
ロックファイルに載っていないワークフローを足してpushし，実行が止まることを確かめる．

## 6-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．
2. `uses:`にタグを書いても，タグの付け替えで別のコードが動かないのはなぜか．ロックファイルの差分のどこを見てレビューするか．
3. 固定すると，actionの修正(セキュリティの修正を含む)が自動では入らなくなる．どう補うか．
4. キーレスの署名で，秘密鍵を保管しないことの利点は何か．
5. `cosign verify`の`--certificate-identity-regexp`を`.*`にすると，何を検証していることになるか．
6. 運用項目と実装を比べ，合わないところがあれば直す．

## 6-7 発展課題

`gate:pinning`に，ワークフローの`permissions`が書かれていなければ失敗する検査を足す．
既定の権限は広いことがあるので，必要な権限だけを書かせる．
テストリスト，設計書，実装の順に進める．
