# 第9回 バックアップとリストア

この回では，データベースを決めた間隔でバックアップし，消せない場所に保管する仕組みを作る．
バックアップは戻せなければ意味がないので，バックアップのたびに新しいデータベースへ戻す訓練も自動で行う．

## 9-1 準備

1. この回から，PostgreSQLのクライアント(`pg_dump`，`pg_restore`，`psql`)を使う．
   VSCodeで「Rebuild Container」を実行し，Dev Containerを作り直す．
2. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

3. この回に仕込む問題はない．問題は，今の題材にはバックアップがないことである．

   ```console
   mise run iteration:start 9
   ```

## 9-2 学ぶこと

### バックアップの要求

規格は次のことを求める．

- ISO/IEC 27001 A.8.13：決めた方針に従ってバックアップを取り，定期的に戻せることを確かめる．
- SOC 2 A1.2，A1.3：データを戻せるようにし，その手順を試す．

バックアップの方針では，次の2つを決める．

- RPO(Recovery Point Objective)：どこまでのデータを失ってもよいか．バックアップの間隔で決まる．
- 保管期間：どこまで遡って戻せる必要があるか．

どちらも方針なので，基準値として`ops/standards.yaml`に書く．

### バックアップを守る

ランサムウェアの攻撃者は，データと一緒にバックアップも消そうとする．
バックアップは，第3回の証跡と同じく，Object Lockを使って消せない形で保管する．

### リストアの訓練

戻したことのないバックアップは，戻せるかどうか分からない．
戻す手順を自動化し，定期的に動かして結果を記録する．
戻した結果が正しいかは，バックアップした時点の各テーブルの行数と比べて確かめる．
今のデータベースと比べると，バックアップの後の変更で数が合わなくなるからである．

### PostgreSQLのバックアップ

`pg_dump --format=custom`は，データベースを1つのファイルに書き出す．
`pg_restore`で，別のデータベースに戻せる．

```console
pg_dump --format=custom --file app.dump "$DATABASE_URL"
pg_restore --no-owner --dbname "$NEW_DATABASE_URL" app.dump
```

### 定期ジョブ

GitHub Actionsの`schedule`は，cronの書き方でワークフローを定期的に動かす．
時刻はUTCである．
`workflow_dispatch`も書くと，画面から手で動かせる．
actでは`act schedule`で，`schedule`のワークフローを手元で動かせる．

## 9-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run ops:backup`は，データベースを書き出してバックアップの保管場所に置く．バックアップした時点の各テーブルの行数も一緒に置く．
- `mise run ops:restore-test`は，最新のバックアップを新しいデータベースに戻し，行数がバックアップした時点と一致するかを確かめる．訓練に使ったデータベースは消す．
- バックアップの保管場所は，基準値の日数だけ消せない．
- どちらの作業も，結果を証跡(`out/evidence/`)と運用の作業の記録に残す．
- `backup.yml`が，基準値の間隔でバックアップと訓練を動かす．

### 作るもの

- `infra/backup.tf`と，バケットの名前の出力．
- `tools/ops/backup.ts`と`tools/ops/restore-test.ts`．コマンドの実行や記録の処理は，共通にできるものを`tools/ops/run.ts`にまとめる．
- `.github/workflows/backup.yml`と，運用テスト`tests/ops/backup.test.ts`．

既存のテストへの影響も考える．
ログの種類が増えると，第8回のログの運用テストはどうなるか．

## 9-4 設計書

第8回の流れのとおり，運用項目の問いから始める．

1. `ops/items.yaml`に，バックアップとリストアの訓練の2つの項目を足す．
   どちらにも，「決めたとおりに行われていたことを，監査人に示す」問いを`records`に書く．
2. 問いに答えるログの種類は，APIのログと監査ログのどちらにも当てはまらない．
   作業の結果を記録する新しい種類を`ops/logs.yaml`に足す．項目は，問いの答えの要るものだけにする．
3. 基準値に，バックアップの間隔と保管期間，新しいログの種類の保管期間を足す．
4. `ops/runbooks/restore.md`に，本当に戻すときの手順を書く．今のデータベースをどうするか，誰に知らせるかも書く．

設計書を書いた時点で`ops:verify`を実行すると，まだないワークフローと手順書を指摘する．

```text
ops/items.yaml: backup: ワークフロー backup.yml がない
ops/items.yaml: backup: 手順書 runbooks/restore.md がない
ops/items.yaml: restore-test: ワークフロー backup.yml がない
ops/items.yaml: restore-test: 手順書 runbooks/restore.md がない
```

## 9-5 テスト駆動の実装

### 運用テスト

先に運用テストを書く．
テストの中で，決まった行数のテーブルを作ってから，バックアップと訓練を動かす．
行数が戻した先と一致することと，作業の記録が`ops`のロググループに残り，ログの設計に合うことを確かめる．

```console
mise run up
mise run test:ops
```

### バックアップと訓練

ヒントは次のとおりである．

- データベースの接続先とバケットの名前は，`tofu -chdir=infra output -raw`で得る．
- 訓練用のデータベースは，AWS CLIの`aws rds create-db-instance`で作り，`aws rds wait db-instance-available`で待つ．
  作れたら，失敗したときも`finally`で消す．
- データベースが接続を受け付けるまでには，少し時間がかかる．`psql`で`SELECT 1`が通るまで待つ．
- 運用の作業の記録は，1行のJSONを標準出力に書き，`LOG_GROUP_PREFIX`があればCloudWatch Logsにも送る．

### backup.yml

`backup.yml`のジョブは，第3回の`evidence`ジョブと同じくMiniStackを起動し，`mise run up`の後でバックアップと訓練を動かす．
actのハッシュの固定(第6回)も忘れずに行う．
手元では次のように動かせる．

```console
act schedule
```

## 9-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．
2. リストアの訓練で，今のデータベースではなく，バックアップした時点の行数と比べるのはなぜか．
3. 行数が一致するだけで，戻した結果が正しいと言えるか．足りないとしたら，何を足すか．
4. CIのジョブの中のデータベースは，ジョブが終わると消える．本物の環境では，このジョブの何が変わるか．
5. 運用項目と実装を比べ，合わないところがあれば直す．
