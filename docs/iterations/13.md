# 第13回 組織への展開

この回では，ここまでの基準と検査を，組織のほかのリポジトリでも使える形にする．
ゲートのジョブを呼び出せるワークフローにまとめ，組織の決まりをconftestのルールとして書く．
あわせて，第6回で署名したイメージを，検証してからデプロイする仕組みを作る．

## 13-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回の問題を当て，コミットする．

   ```console
   mise run iteration:start 13
   git add -A
   git commit -m "本番へのデプロイを作る"
   ```

3. `.github/workflows/deploy.yml`と`tools/ops/deploy.ts`を読む．
   デプロイされるイメージが，第6回の`release.yml`で作ったものだと言えるか．

## 13-2 学ぶこと

### 組織で同じ基準を使う

規格は次のことを求める．

- NIST SSDF PO.1：組織のソフトウェア開発のセキュリティの要求を決め，保つ．
- ISO/IEC 27001 A.5.1：方針を決め，関係する人に伝え，守られていることを確かめる．

リポジトリごとに検査を書き写すと，基準が少しずつずれる．
基準を1か所に置き，どのリポジトリもそれを参照する形にする．

### reusable workflow

`on: workflow_call`を書いたワークフローは，ほかのワークフローからジョブとして呼べる．
これをreusable workflowという．

```yaml
# 呼ばれる側(.github/workflows/gates.yml)
on:
  workflow_call:
    inputs:
      working-directory:
        type: string
        default: app
```

```yaml
# 呼ぶ側
jobs:
  gates:
    uses: ./.github/workflows/gates.yml                       # 同じリポジトリ
    # uses: <owner>/<repo>/.github/workflows/gates.yml@<ハッシュ>  # ほかのリポジトリ
```

呼ばれた側のジョブが残したartifactは，呼んだ側のジョブから`actions/download-artifact`で取れる．

### conftest

conftestは，YAMLやJSONなどの設定ファイルを，Regoという言語のルールに照らして検査する道具である．
ルールは`deny`の集合に，決まりに反したときのメッセージを足す形で書く．

```rego
package workflows

deny contains msg if {
	not input.permissions
	msg := "最上位に permissions を書いていない"
}
```

`conftest test --policy policy --namespace workflows <ファイル>`で，`package workflows`のルールで検査する．
`--output json`で，ファイルごとの結果をJSONで得られる．
ルールのディレクトリは`conftest pull`でGitのリポジトリなどから取得できるので，組織で1か所に置ける．

### デプロイの前の検証

SLSAは，ビルドの出どころ(provenance)を残し，使う側で確かめることを求める．
第6回では，イメージに署名とprovenanceを付けた．
付けただけでは，デプロイするときに確かめなければ，すり替えられたイメージも動いてしまう．
検証してからデプロイし，検証したものと同じイメージを使うために，ダイジェストで指定する．

## 13-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run gate:policy`は，`policy/`のルールで，ワークフローと運用項目を検査する．次のどれかがあれば失敗する．
  - 最上位に`permissions`のないワークフロー．
  - 同じジョブの中で，`mise run release:verify`より前に`mise run deploy`を動かすワークフロー．
  - 人が行う運用項目(`actor: 人`)で，手順書のないもの．
- `mise run deploy`は，ダイジェストで指定していないイメージをデプロイしない．
- `deploy.yml`は，タグからダイジェストを得て，署名とprovenanceを検証してからデプロイする．
- ゲートのジョブは`gates.yml`にまとめ，`ci.yml`はそれを呼ぶ．

### 作るもの

- `policy/workflows.rego`と`policy/items.rego`．
- `tools/gates/policy.ts`：`--workflows`，`--items`，`--policy`で入力を変えられるようにする．
- `mise.toml`の`gate:policy`タスク．
- `.github/workflows/gates.yml`．

既存のテストへの影響も考える．
ゲートのジョブを`gates.yml`に移すと，`ops:verify`は何を指摘するか．

## 13-4 設計書

- `ops/items.yaml`：組織の共通ルールの適用と，デプロイ前の検証の2つを足す．
  デプロイには，本番で動くイメージを，いつ誰の操作でデプロイしたかを示す問いを`records`に書く．
- `ops/runbooks/shared-policy.md`：ほかのリポジトリでの使い方と，ルールの変え方を書く．
- `ops/runbooks/verify-image.md`：デプロイの手順を足す．
- `ops/policy.md`：共通のルールを変えるときの承認の流れと，デプロイの決まりを書く．
- `.github/CODEOWNERS`：`policy/`と`gates.yml`を，セキュリティ責任者の承認対象にする．

## 13-5 テスト駆動の実装

### gate:policy

ルールを書いて実行すると，仕込まれた`deploy.yml`が見つかる．

```text
deploy.yml: ジョブ deploy が，mise run release:verify より前に mise run deploy を動かしている
```

ヒントは次のとおりである．

- `some i, step in job.steps`で，ステップとその番号を順に取り出せる．
- 「前に検証がある」は，番号が`i`より小さく，`run`に`mise run release:verify`を含むステップがあること，と書ける．
- `conftest test`は，ルールに反すると終了コード1を返す．それ以外の失敗(ルールの書き間違いなど)と区別する．

### デプロイを直す

1. `deploy.ts`に，ダイジェストで指定されているかを確かめる関数を足し，単体テストを書く．
2. `deploy.yml`で，タグからダイジェストを得る．

   ```console
   docker buildx imagetools inspect ghcr.io/<owner>/<repo>/api:<タグ> --format '{{json .Manifest.Digest}}'
   ```

3. 第6回の`mise run release:verify`で検証してから，AWSの認証情報を得てデプロイする．
4. 入力のタグや，そこから作った値は，`run`に`${{ }}`で直接書かず，`env`で渡す．

### gates.yml

1. `ci.yml`のゲートのジョブを`gates.yml`へ移し，`working-directory`を入力にする．
2. `ci.yml`は`gates.yml`を呼び，`evidence`ジョブは`needs: [gates]`にする．
3. `mise run ops:verify`の指摘に従い，運用項目の仕組みを`gates.yml`に替える．
4. `mise run ci`で，呼び出しが動くことを確かめる．

```console
mise run up
mise run test:ops
```

テストリスト，設計書，実装の順に進める．
