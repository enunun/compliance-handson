# 第7回 監視とアラート

この回では，題材のSaaSの異常に気づいて担当者に知らせる仕組みを作る．
APIの数値をPrometheusで集め，エラーの増加をAlertmanagerが知らせる．状況はGrafanaで見られるようにする．

## 7-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回に仕込む問題はない．問題は，今の題材ではAPIのエラーが増えても誰も気づかないことである．

   ```console
   mise run iteration:start 7
   ```

## 7-2 学ぶこと

### 監視の要求

規格は次のことを求める．

- ISO/IEC 27001 A.8.16：ネットワーク，システム，アプリケーションの異常な振る舞いを監視し，対処する．
- SOC 2 CC7.2：システムの構成要素を監視し，異常を見つける．

監視の仕組みは，「何を測るか」「どこからを異常とするか」「誰に知らせるか」の3つを決めて作る．
どこからを異常とするか(しきい値)は方針なので，基準値として`ops/standards.yaml`に書く．

### Prometheus

Prometheusは，各サービスの`/metrics`から数値(メトリクス)を定期的に集めて保存する．
Goでは`github.com/prometheus/client_golang`でメトリクスを作る．

```go
requests := prometheus.NewCounterVec(prometheus.CounterOpts{
	Name: "http_requests_total",
	Help: "処理したHTTPのリクエストの数",
}, []string{"route", "code"})
requests.WithLabelValues("GET /api/notes", "500").Inc()
```

数値の問い合わせにはPromQLを使う．
例えば，直近5分間の5xxの割合は次のように書く．

```text
sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))
```

アラートのルールは，PromQLの式と，その状態が続く時間(`for`)で書く．

```yaml
groups:
  - name: example
    rules:
      - alert: TooManyErrors
        expr: <PromQLの式> > 0.1
        for: 5m
        labels:
          severity: page
```

### ルールのテスト

`promtool test rules`は，時系列のデータを与えて，ある時点でアラートが発火しているかを確かめる．
`values: "0+10x30"`は，0から始めて1つの間隔ごとに10ずつ増える値を30回並べる書き方である．

```yaml
tests:
  - interval: 1m
    input_series:
      - series: 'http_requests_total{code="500"}'
        values: "0+10x30"
    alert_rule_test:
      - eval_time: 10m
        alertname: TooManyErrors
        exp_alerts: []
```

### Alertmanager

Alertmanagerは，Prometheusからアラートを受け取り，ラベルで通知先を振り分ける．
`amtool config routes test`で，あるラベルのアラートがどの通知先に届くかを確かめられる．

```console
amtool config routes test --config.file alertmanager.yml --verify.receivers on-call severity=page
```

### Grafana

Grafanaは，Prometheusの数値をグラフにする．
データソースとダッシュボードを設定ファイル(provisioning)で用意すると，画面での手作業なしに同じ環境を作れる．

## 7-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．
単体テスト，運用テストを分けて書く．

### 要求

- APIは，`/metrics`で，ルートとステータスコードごとのリクエストの数と，処理の時間を返す．
- 5xxの割合が基準値を超えた状態が，基準値の時間だけ続いたら，アラート`ApiHighErrorRate`が発火する．
  割合が下がれば止む．割合が低ければ発火しない．
- `severity: page`のアラートはオンコールの担当者に，それ以外はチームのチャットに知らせる．
- アラートのルールは基準値から生成し，`ops:verify`が基準値と合うかを確かめる．
- 運用項目の仕組みに，アラートのルールを書ける．`ops:verify`は，そのアラートがルールにあるかを確かめる．

### 作るもの

- `apps/api/internal/server/metrics.go`：メトリクスと，ハンドラを数える関数．
- `tools/ops/alerts.ts`：基準値からアラートのルールを作る関数．`ops:render`がファイルに書く．
- `ops/monitoring/`：`prometheus.yml`，`rules.yml`(生成)，`alertmanager.yml`，Grafanaの設定．
- `tests/ops/alert-rules.test.yml`と，`mise.toml`の`test:alerts`タスク．

既存のテストへの影響も考える．
運用項目のスキーマの「仕組み」を，どう変えればアラートも書けるか．

## 7-4 設計書

- `ops/standards.yaml`：エラーの割合のしきい値と，続く時間を足す．
- `ops/items.yaml`：APIの監視の項目を足す．仕組みは`alert: ApiHighErrorRate`である．
- `ops/runbooks/api-high-error-rate.md`：アラートが来たときの対応を書く．どこを見て，何を確かめ，いつ人を呼ぶか．
- `ops/policy.md`：アラートの通知先を，連絡先の表に足す．

## 7-5 テスト駆動の実装

### メトリクス

APIの単体テストで，リクエストの後に`/metrics`を読み，数が増えていることを確かめる．
ステータスコードを数えるには，`http.ResponseWriter`を包み，`WriteHeader`で渡された値を覚える．

### アラートのルール

先に`tests/ops/alert-rules.test.yml`を書き，ルールがない状態で失敗することを確かめる．
ルールの式を誤ると(例えばしきい値を0.2にすると)，次のように失敗する．

```text
  FAILED:
    alertname: ApiHighErrorRate, time: 15m, 
        exp:[
            0:
              Labels:{alertname="ApiHighErrorRate", severity="page"}
              Annotations:{runbook="ops/runbooks/api-high-error-rate.md", summary="APIのエラーの割合が5%を超えている"}
            ], 
        got:[]
```

ヒントは次のとおりである．

- `rate`は5分の窓を使うので，発火するのは，割合が上がってから窓が埋まり，さらに`for`の時間がたった後である．
  `eval_time`はそれを見越して選ぶ．
- 生成したYAMLの先頭に，手で編集しないことをコメントで書く．`yaml`の`stringify`の`lineWidth: 0`で，長い式を折り返さないようにする．

### 通知先とDev Container

1. `alertmanager.yml`で，`severity="page"`をオンコールの担当者へ振り分ける．
2. `test:alerts`タスクに次のコマンドを並べ，`check:code`に足す．
   - `promtool check config`と`promtool test rules`
   - `amtool check-config`と`amtool config routes test`
3. `.devcontainer/compose.yml`に，Prometheus，Alertmanager，Grafanaを足す．設定は`app/ops/monitoring/`をコンテナに渡す．
4. VSCodeで「Rebuild Container」を実行し，APIを起動する．
   <http://localhost:9090>でPrometheusの「Alerts」，<http://localhost:3001>でGrafanaの「API」のダッシュボードを開く．

## 7-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．
2. しきい値を基準値に書き，ルールを生成するのはなぜか．ルールのファイルに直接書くと何が起きるか．
3. `for: 5m`がないと，何が起きるか．
4. アラートの手順書に，「いつ人を呼ぶか」まで書くのはなぜか．
5. 運用項目と実装を比べ，合わないところがあれば直す．

## 7-7 発展課題

APIの処理の時間の95パーセンタイルが1秒を超えたら知らせるアラートを足す．
しきい値は基準値に書く．重大度は，チームのチャットへ届くものにする．
テストリスト，設計書，実装の順に進める．
