# 第4回 SAST

この回では，コードに潜む脆弱性(SQLインジェクションやXSSなど)を，コードを読んで見つけるゲートを作る．
見つかったもののうち，前提が成り立たない誤検知は，基準を決めて例外にする．

## 4-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回の問題を当て，コミットする．

   ```console
   mise run iteration:start 4
   git add -A
   git commit -m "メモを検索できるようにし，改行を表示する"
   ```

3. APIの`GET /api/notes?q=...`と，Web画面のメモの表示がどう変わったかを読む．

## 4-2 学ぶこと

### SAST

SAST(Static Application Security Testing)は，プログラムを動かさずにコードを調べ，脆弱性になりやすい書き方を見つける検査である．
第2回のSCAが他人のコード(依存関係)を調べるのに対し，SASTは自分たちのコードを調べる．

規格は次のことを求める．

- ISO/IEC 27001 A.8.28：安全なコーディングの原則をソフトウェアの開発に適用する．
- NIST SSDF PW.7：コードをレビューし，解析して脆弱性を見つける．

### Semgrep

Semgrepは，コードの形(パターン)でルールを書いて検査する道具である．
レジストリには言語ごとのルールセット(`p/golang`，`p/typescript`など)がある．

```console
semgrep scan --config p/golang --config .semgrep --json-output result.json .
```

`--config`には，レジストリのルールセットと，自前のルールのファイルやディレクトリを並べて渡せる．

レジストリのルールセットは，標準ライブラリやよく使われるライブラリの危ない書き方を見つける．
一方で，題材が使うpgxやHonoのような個々のライブラリの書き方までは見ていないことがある．
そのときは，自前のルールを書く．

```yaml
rules:
  - id: no-eval
    languages: [typescript]
    severity: ERROR
    message: eval() に文字列を渡さない．
    patterns:
      - pattern: eval($X)
      - pattern-not: eval("...")
```

- `pattern`：見つけたい形．`$X`はメタ変数で，任意の式に当たる．`...`は任意の引数や文に当たる．
- `pattern-either`：どれかに当たれば検出する．
- `pattern-not`：当たっても除く形．
- `metavariable-regex`：メタ変数の名前などを正規表現で絞る．`patterns`の中に書く．

Semgrepは既定で`tests/`の下のファイルを調べない．
リポジトリ直下に`.semgrepignore`を置くと，既定の除外を置き換えられる．

### SQLインジェクションとXSS

SQLインジェクションは，利用者の入力がSQLの文の一部として解釈される脆弱性である．
値はSQLの文字列に埋め込まず，プレースホルダーで渡す．
pgxでは`$1`，`$2`のように書き，値を引数で渡す．

XSS(クロスサイトスクリプティング)は，利用者の入力がHTMLとして解釈される脆弱性である．
HonoのJSXは，`{値}`をエスケープしてから出力する．
`hono/html`の`raw()`は，エスケープせずに出力する．

### 誤検知

SASTは，コードの形だけで判断するので，前提が成り立たない場合も検出する．
例えば，弱いハッシュ関数(SHA-1)の検出は，用途が署名や改ざんの検知なら問題になるが，キャッシュの判定なら問題にならない．
誤検知を例外にするときは，判断の基準を手順書に書く．誰が判断しても同じ結論を得られるようにするためである．

## 4-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run gate:sast`は，SQLを文字列の組み立てで作るコードと，`raw()`に変数を渡すコードがあれば失敗する．
  見つけた場所とルールを表示する．
- 直したコードでは通る．
- 例外に載った検出は，期限まで外す．例外は，ルールの識別子とファイルで場所を絞れる．
- 結果を，JSONとSARIFで`out/evidence/sast/`に残す．

### 作るもの

- `.semgrep/rules.yml`：pgxの`Query`，`QueryRow`，`Exec`にSQLの組み立て(`fmt.Sprintf`や`+`)を渡すコードと，`raw()`に文字列の定数以外を渡すコードを見つけるルール．
- `tools/gates/sast.ts`：`--target`と`--exceptions`で入力を変えられるようにする．
- `mise.toml`の`gate:sast`タスクと，リポジトリ直下の`.semgrepignore`．

既存のテストへの影響も考える．
APIの`Store`に検索の関数が足されたことで，どのテストのコードが変わったか．

## 4-4 設計書

- `ops/items.yaml`：SASTの項目を足す．
- `ops/schema/exceptions.schema.json`：例外にファイルを書く`path`を足す．
- `ops/runbooks/exception-request.md`：誤検知と判断する基準を足す．
  どんな場合に誤検知としてよく，どんな場合は直すかを書く．

## 4-5 テスト駆動の実装

### 自前のルールとゲート

ゲートのテストの入力は4つ用意する．SQLの組み立て，`raw()`，直したコード，SHA-1を，それぞれ1つずつ含むものである．
Semgrepの結果のJSONでは，検出が`results`の配列に入り，それぞれが`check_id`(ルールの識別子)，`path`，`start.line`を持つ．

題材に対して実行すると，4件見つかる．

```text
apps/api/cmd/api/main.go:33: [go.lang.security.audit.net.use-tls.use-tls] Found an HTTP server without TLS. Use 'http.ListenAndServeTLS' instead. See https://golang.org/pkg/net/http/#ListenAndServeTLS for more information.
apps/api/internal/server/server.go:84: [go.lang.security.audit.crypto.use_of_weak_crypto.use-of-sha1] Detected SHA1 hash algorithm which is considered insecure. SHA1 is not collision resistant and is therefore not suitable as a cryptographic signature. Use SHA256 or SHA3 instead.
apps/api/internal/store/postgres.go:112: [semgrep.pgx-sql-built-from-string] SQLを文字列の組み立てで作っている．利用者の入力が混ざるとSQLインジェクションになる． 値はSQLの文字列に埋め込まず，プレースホルダーで渡す．
apps/web/src/app.tsx:127: [semgrep.hono-raw-with-variable] hono/html の raw() は，渡した文字列をエスケープしない． 利用者の入力が混ざるとXSSになる．JSXの中に値をそのまま書けばエスケープされる．
```

ヒントは次のとおりである．

- 題材全体を調べるときは，ゲートのテストの入力を`--exclude`で外す．ゲートのテストの入力を調べるときは外さない．
- Semgrepそのものの失敗(終了コードが0以外)は，検出の有無と区別して知らせる．

### 検出への対応

1. SQLは，検索の語をプレースホルダーで渡す形に直す．`LIKE`のパターンは，SQLの中で`'%' || $2 || '%'`のように組み立てる．
2. 改行の表示は，行に分けてJSXで`<br />`を挟む形に直す．
   直した後も改行が表示され，`<script>`のようなHTMLがエスケープされることを，Web画面の単体テストで確かめる．
3. SHA-1とTLSの検出は，手順書の基準に照らして判断し，誤検知なら例外を申請する．

### CI

`ci.yml`に`sast`ジョブを足し，結果をartifactに残す．
`evidence`ジョブの`needs`にも足す．

## 4-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．
2. レジストリのルールセットだけでは，この回の仕込みが見つからなかったのはなぜか．
3. SHA-1の検出を，SHA-256に替えて直す方法もある．例外にする場合と比べ，どちらを選ぶか．
4. 自前のルールが誤った形を見つけるようになると(例えば`w.Header().Set`にも当たる)，何が起きるか．ルールにもテストが要るのはなぜか．
5. 運用項目と実装を比べ，合わないところがあれば直す．
