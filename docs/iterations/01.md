# 第1回 シークレット検出

この回では，APIキーやパスワードなどのシークレットがリポジトリに入るのを止める仕組みを作る．
コミットの前に止める検査と，履歴全体を調べる検査の2つを作り，入ってしまったときの対応も手順書にする．

## 1-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回の問題を当て，そのままコミットする．
   チームの誰かが，メール配信サービスのクライアントを足したという想定である．

   ```console
   mise run iteration:start 1
   git add -A
   git commit -m "メール配信のクライアントを足す"
   ```

3. `apps/api/internal/mail/mail.go`を開き，何が問題かを考える．

## 1-2 学ぶこと

### シークレットが漏れるということ

シークレットは，一度でもgitの履歴に入れば漏れたものとして扱う．
後のコミットで消しても，履歴，fork，手元のcloneに残るからである．
そのため，漏れたときの対応は「履歴から消す」より先に「発行元で無効化し，新しいものに替える」ことである．

規格は次のことを求める．

- ISO/IEC 27001 A.5.17：認証情報を適切に管理する．
- NIST SSDF PS.1：コードを不正なアクセスや改ざんから守る．

### gitleaks

gitleaksは，ファイルやgitの履歴からシークレットを探す道具である．
クラウドやSaaSのキーの形式ごとのルールと，`api_key = "..."`のような書き方を見つける汎用のルール(`generic-api-key`)を持つ．
汎用のルールは，値の乱雑さ(エントロピー)が高いものだけを検出する．

```console
gitleaks git --redact -v <リポジトリ>                # 履歴全体を調べる
gitleaks git --redact --pre-commit --staged <リポジトリ>  # ステージした変更だけを調べる
```

`--redact`を付けると，出力と結果のファイルでシークレットを伏せ字にする．
結果を証跡として残すときに，証跡そのものがシークレットを含まないようにするためである．

検出から外したいものは，設定ファイル(`.gitleaks.toml`)の`[[allowlists]]`に書く．
ファイルの場所(`paths`)や，値の正規表現(`regexes`)で指定できる．

```toml
[extend]
useDefault = true  # 既定のルールを使い，その上に設定を足す

[[allowlists]]
description = "外す理由"
paths = ['''^docs/examples/''']
```

### コミットの前に止める

lefthookは，gitのフックを設定ファイル(`lefthook.yml`)で管理する道具である．
Dev Containerの`mise run setup`が，すでにフックを有効にしている．
`pre-commit`にコマンドを足すと，コミットのたびに実行され，失敗するとコミットが止まる．

### CIの証跡

GitHub Actionsでは，`actions/upload-artifact`で，ジョブが作ったファイルを実行の記録に残せる．
`if: always()`を付けると，前の手順が失敗したときも残す．
`actions/checkout`は既定で最新のコミットだけを取得するので，履歴を調べるジョブでは`fetch-depth: 0`を指定する．

## 1-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run gate:secrets`は，gitの履歴全体からシークレットを探し，見つけたら失敗する．
  引数でリポジトリの場所を変えられる．
- `mise run gate:secrets:staged`は，コミットしようとしている変更からシークレットを探し，見つけたら失敗する．
  引数でリポジトリの場所を変えられる．
- どちらも，出力と結果のファイル(`out/evidence/secrets/gitleaks.json`)にシークレットそのものを書かない．
- ゲートのテストとその入力(fixture)，無効化したキーは，検出から外す．
- コミットのたびに`gate:secrets:staged`が実行される．
- CIの`secrets`ジョブが`gate:secrets`を実行し，結果をartifactとして残す．

### 作るもの

- `mise.toml`の`gate:secrets`と`gate:secrets:staged`タスク．
- リポジトリ直下の`.gitleaks.toml`．
- `lefthook.yml`のコマンドと，`ci.yml`の`secrets`ジョブ．

ゲートのテストは，fixtureを中身にした一時的なgitのリポジトリを作り，そのリポジトリを引数に渡して確かめる．
fixtureには，題材の仕込みとは別の形のキーを使う．

既存のテストへの影響も考える．
ゲートが増えたので，`mise run check`の中身をどう分けるかも考える．

## 1-4 設計書

- `ops/items.yaml`：`secret-detection`を足す．
  仕組みは`ci.yml`の`secrets`ジョブで，タイミングはコミットごとと変更ごとである．
  分類は，漏洩という情報の扱いを統制する運用として考える．
- `ops/runbooks/secret-leak.md`：漏れたときの対応を書く．
  無効化，交換，利用の確認，許可リストへの記録の順と，記録を残す表を含める．
- `ops/policy.md`：漏洩を最初に誰へ知らせるかを，連絡先として足す．

## 1-5 テスト駆動の実装

### gate:secrets

一時的なリポジトリを作る関数を，テストのファイルに書く．
`node:fs`の`mkdtempSync`と`cpSync`，`helpers.ts`の`run`で`git init`，`git add`，`git commit`を実行する．
miseのタスクに引数を渡すと，`run`の最後のコマンドの末尾に付く．

```console
mise run gate:secrets /tmp/gate-secrets-xxxx
```

結果のファイルの置き場所は，gitleaksが作らないので先に`mkdir -p`で作る．
`run`に配列を書くと，コマンドを順に実行する．

### gate:secrets:staged

ステージだけしてコミットしていないリポジトリで確かめる．
コミットが1つもないリポジトリでは差分を取れないので，空のコミットを先に作っておく．

### 検証のコマンドとCI

`check`を次の3つに分ける．

- `check:code`：lint，単体テスト，ゲートのテスト，`ops:verify`．CIの`check`ジョブが実行する．
- `gates`：すべてのゲート．CIでは，ゲートごとのジョブで実行する．
- `check`：`check:code`と`gates`．手元でまとめて確かめるときに使う．

`ci.yml`の`check`ジョブを`mise run check:code`に替え，`secrets`ジョブを足す．
`mise run ci`で，2つのジョブが成功することを確かめる．

### 仕込まれたキーへの対応

ゲートができたら，題材に対して実行する．
履歴に残ったキーが見つかって失敗する．

```text
Finding:     apiKey: "REDACTED"
Secret:      REDACTED
RuleID:      generic-api-key
Entropy:     4.171861
File:        app/apps/api/internal/mail/mail.go
Line:        11
...
WRN leaks found: 1
```

手順書のとおりに対応する．
この演習では，発行元での無効化は済んだものとして進める．

1. `mail.go`を，APIキーを引数で受け取る形に直す．
2. 無効化したキーを，`.gitleaks.toml`の許可リストに足す．
   値の正規表現で指定し，理由と手順書の記録欄を示すコメントを書く．
3. 手順書の記録欄に，対応の記録を書く．
4. `mise run gate:secrets`が通ることを確かめる．

## 1-7 発展課題

汎用のルールより確実に検出できる．
テストリスト，設計書，実装の順に進める．
