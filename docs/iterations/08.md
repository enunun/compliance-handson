# 第8回 ログ設計

この回では，ログを「何となく出すもの」から「運用の問いに答えるための記録」に変える．
まず運用項目ごとに，ログで答える問いを書き出し，そこからログの種類，項目，保管期間，閲覧できる人を導く．
そのうえで，設計どおりのログをAPIに出させ，実際のログが設計に合うことをテストで確かめる．

## 8-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回の問題を当て，コミットする．

   git commit -m "ログインとメモの作成のログを足す"

   障害の調査，監査，不正の調査のそれぞれで，このログが役に立つか．

## 8-2 学ぶこと

### ログの要求

規格は次のことを求める．

- ISO/IEC 27001 A.8.15：活動，例外，障害などの記録を取り，保管し，守り，分析する．
- ISO/IEC 27001 A.8.16：異常な振る舞いを監視する(第7回)．その調査にもログを使う．
- SOC 2 CC7.2：異常を見つけて分析する．

規格は「何を記録するか」を細かく決めない．
決めるのは組織である．
決め方の筋道は，運用から逆算することである．

### 運用からログを導く

ログの設計は，次の順に進める．

1. 運用項目ごとに，ログで答える問いを書く．
   誰が(問う人)，何を(問い)，いつまでに(答える期限)，どこまで遡って(遡る期間)知りたいかを書く．
2. 問いをまとめて，ログの種類を分ける．
   読む人と保管期間が大きく違う問いは，別の種類にする．例えば障害の調査と監査では，読む人と期間が違う．
3. 種類ごとに，問いの答えに要る項目を決める．記録してはならない項目(パスワード，トークンなど)も決める．
4. 種類ごとの保管期間を，その種類を使う問いの遡る期間のうち最も長いものに合わせる．
5. 実装と基盤(ロググループと保管期間)を，決めた種類と項目に従わせる．

この講座では，1を運用項目の`records`に，2と3を`ops/logs.yaml`に，4を基準値の`logs.retention_days`に書く．
そうすると，「この項目は何のためにあるのか」「この保管期間の根拠は何か」を，設計書から辿れる．

### 構造化ログ

構造化ログは，1行を1つのJSONのような決まった形で書くログである．
項目で検索でき，機械で検証できる．
Goでは標準ライブラリの`log/slog`で書ける．

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
logger.Info("request handled", "request_id", id, "status", 200)
// {"time":"...","level":"INFO","msg":"request handled","request_id":"...","status":200}
```

リクエストごとに識別子(リクエストID)を付け，応答のヘッダ(`X-Request-Id`)とすべてのログに入れると，1つのリクエストのログを追える．

### CloudWatch Logs

CloudWatch Logsは，ログをロググループに集めて保管する．
ロググループごとに保管期間と閲覧の権限を決められるので，ログの種類ごとにロググループを分ける．
AWS SDK for Go v2の`cloudwatchlogs`で書き込み，AWS CLIの`aws logs filter-log-events`で検索する．

```console
aws logs filter-log-events --log-group-name /app/audit --filter-pattern '{ $.action = "login.failed" }'
```

## 8-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．
単体テスト，ゲートのテスト，運用テストを分けて書く．

### 要求

- APIは，リクエストごとに，リクエストID，ルート，ステータスコード，処理の時間を`api`のログに1行書く．応答にも`X-Request-Id`を付ける．
- ログインの成功と失敗，権限の変更を，誰が誰に何をしたかとともに`audit`のログに書く．
- どのログにも，パスワードとトークンを書かない．
- `LOG_GROUP_PREFIX`があれば，ログを種類ごとのロググループ(`/app/api`，`/app/audit`)にも送る．
- `ops:verify`は，`records`が使うログの種類と項目が`ops/logs.yaml`にあること，保管期間が遡る期間以上であることを確かめる．
- 本番の環境のロググループの各行は，`ops/logs.yaml`の設計に合う．ロググループの保管期間は基準値と同じである．

### 作るもの

- `tools/ops/logs.ts`：`records`とログの設計の照らし合わせ，ログの1行を検証するJSON Schemaの生成，対応表(`ops/records.md`)の生成．
- `apps/api/internal/server/logging.go`：リクエストのログと監査のログを書く関数．
- `apps/api/internal/logging/cloudwatch.go`：ログを`log_type`の値ごとのロググループにも送る`slog.Handler`．
- `infra/logging.tf`と，運用テスト`tests/ops/logs.test.ts`．

既存のテストへの影響も考える．
`server.New`にロガーを渡すようにすると，どのテストのコードが変わるか．

## 8-4 設計書

この回の中心である．8-2の順に進める．

1. `ops/items.yaml`の`service-monitoring`に，アラートの原因になったリクエストを特定する問いを書く．
2. 監査ログの項目`audit-logging`を足し，権限の変更を示す問いと，ログインの失敗が続くアカウントを見つける問いを書く．
3. ログの設計の項目`log-design`を足す．仕組みは`ops:verify`を実行する`check`ジョブである．
4. `ops/logs.yaml`とそのスキーマを書く．問いの項目を，種類ごとの項目に集める．
5. 基準値に`logs.retention_days`を足す．
6. `ops/policy.md`に，ログの種類ごとの閲覧できる人を書く．
7. 手順書`api-high-error-rate.md`に，リクエストIDでログを追う手順を足す．

## 8-5 テスト駆動の実装

### 設計の検証

`ops:verify`のゲートのテストに，問いがログの設計にない項目を使う場合と，保管期間が短い場合のfixtureを足す．
実装すると，次のように失敗する．

```text
tests/gates/fixtures/ops-verify/records-missing-field/ops/items.yaml: change-management: ログの種類 api に項目 route がない
tests/gates/fixtures/ops-verify/records-short-retention/ops/items.yaml: ログの種類 api の保管期間(30日)が，問いの keep_days(90日)より短い
```

`ops:render`で，運用項目とログの対応表(`ops/records.md`)も作る．

### APIのログ

APIの単体テストでは，ロガーの出力先を`bytes.Buffer`にし，1行ずつJSONとして読んで確かめる．
パスワードを書かないことは，失敗したログインのリクエストに使ったパスワードが，出力のどこにもないことで確かめる．

ヒントは次のとおりである．

- リクエストIDは，ハンドラを包む関数で作り，`context`に入れて渡す．
- 監査のログでは，`slog.Attr`を並べて項目を足す．
- CloudWatch Logsへ送るハンドラは，次の`slog.Handler`(標準出力)に書いた後で，同じJSONの1行を送る．`log_type`のないログは送らない．
  単体テストでは，CloudWatch Logsのクライアントをインターフェースにして，偽物に差し替える．

### 運用テスト

1. `infra/logging.tf`で，基準値の`logs.retention_days`の種類ごとにロググループを作り，`mise run up`で適用する．
2. 運用テストで，APIをビルドして起動し，ログインの失敗，ログイン，権限の変更をする．
3. 各ロググループの行を，`ops/logs.yaml`から作ったJSON Schemaで検証する．設計にない項目があれば失敗する．

```console
mise run test:ops
```

AWS CLI(v1)は`AWS_REGION`を読まないので，リージョンは`.devcontainer/aws-config`に書いてある．

### CI

`evidence`ジョブのMiniStackに`/var/run/docker.sock`を渡し，RDSのコンテナを動かせるようにする．
運用テストが本物のAPIとデータベースを使うからである．

## 8-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．
2. 監査ログを障害の調査のログと別の種類にしたのはなぜか．同じ種類にすると，保管期間と閲覧の権限はどうなるか．
3. ログインの失敗の監査ログにメールアドレスを書いた．これは個人情報である．書く理由と，守るための決まりを説明する．
4. ログの設計にない項目を，開発者が気軽にログに足すと何が起きるか．運用テストはそれをどう止めるか．
5. 運用項目と実装を比べ，合わないところがあれば直す．

## 8-7 発展課題

ログインの失敗が同じメールアドレスで10分間に5回を超えたら知らせる仕組みを考える．
まず`records`に問いを書き，ログの設計に足りない項目がないかを確かめる．
テストリスト，設計書，実装の順に進める．
