# 第2回 依存関係の脆弱性検査と例外

この回では，既知の脆弱性を持つ依存関係が本番に入るのを止めるゲートを作る．
すぐに直せない脆弱性は，期限と承認者を決めて例外として受け入れ，期限を過ぎた例外もゲートで止める．

## 2-1 準備

1. 題材の検査が通ることを確かめる．

   ```console
   cd app
   mise run check
   ```

2. この回の問題を当て，コミットする．

   ```console
   mise run iteration:start 2
   mise run install
   git add -A
   git commit -m "メモの表示を短くし，配信用のトークンを作る"
   ```

3. `apps/web/package.json`と`apps/api/go.mod`で，足された依存関係を確かめる．
   `apps/api/internal/token/token.go`が，その依存関係で何をしているかも読む．

## 2-2 学ぶこと

### 依存関係の脆弱性

題材のコードの多くは，他人が書いたパッケージである．
パッケージに脆弱性が見つかると，CVE(Common Vulnerabilities and Exposures)の識別子が付き，データベースに登録される．
依存関係をデータベースと照らし合わせる検査を，SCA(Software Composition Analysis)と呼ぶ．

脆弱性には，CVSSなどで決めた重大度(LOW，MEDIUM，HIGH，CRITICAL)がある．
どの重大度から止めるかは，組織の方針である．
この講座では基準値として`ops/standards.yaml`に書く．

規格は次のことを求める．

- ISO/IEC 27001 A.8.8：技術的な脆弱性の情報を得て，評価し，対処する．
- SOC 2 CC7.1：脆弱性を見つける手順を持つ．

### 到達可能性

脆弱性があるパッケージを使っていても，脆弱な関数を呼んでいなければ攻撃されない．
これを「到達しない」と言う．
到達しないことを確かめた脆弱性は，すぐに直さずに受け入れてよい場合がある．
ただし，コードが変わると到達するようになりうるので，期限を決めて見直す．

### Trivy

Trivyは，ロックファイル(`pnpm-lock.yaml`，`go.sum`など)から依存関係を読み，脆弱性のデータベースと照らし合わせる．

```console
trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 .
```

`--exit-code 1`を付けると，見つかったときに終了コードが1になる．
`--format json --output <ファイル>`で結果をJSONで残し，`trivy convert --format table <ファイル>`で人が読む表にできる．

外したい脆弱性は，`--ignorefile`で渡す設定ファイルに書く．
`.trivyignore.yaml`の形では，期限(`expired_at`)を書ける．
期限を過ぎた行は，Trivyが無視する．

```yaml
vulnerabilities:
  - id: CVE-2020-0001
    statement: 外す理由
    expired_at: 2026-12-31
```

### 例外の管理

例外は，申請，承認，期限の3つがそろって初めて管理できる．

- 申請：誰が，なぜ受け入れたいのかを書く．
- 承認：方針を決める人が確かめる．この題材ではCODEOWNERSで承認を必須にする．
- 期限：いつまでに直すか，見直すかを決める．期限が長すぎないよう，最長の日数を基準値で決める．

## 2-3 テストリスト

次の要求を満たすテストのリストを，`TESTLIST.md`に書く．

### 要求

- `mise run gate:sca`は，基準値の重大度以上の脆弱性があれば失敗する．なければ通る．
- 例外に載った脆弱性は，期限まで外す．期限を過ぎた例外では外さない．
- 結果をJSONで`out/evidence/sca/`に残す．
- `mise run gate:exceptions`は，期限を過ぎた例外と，期限が基準値の最長の日数を超える例外があれば失敗する．
- `ops:verify`は，例外の一覧もスキーマで検証する．

### 使用例

```console
$ mise run gate:exceptions
exceptions: 1 active, 0 expired
```

### 作るもの

- `tools/gates/sca.ts`：基準値と例外を読み，Trivyの除外の設定を作ってTrivyを実行する．
  `--target`(調べる場所)と`--exceptions`(例外の一覧)で入力を変えられるようにする．
- `tools/gates/exceptions.ts`：`--exceptions`と`--today`(今日の日付)で入力を変えられるようにする．
- `mise.toml`の`gate:sca`と`gate:exceptions`タスク．

ゲートのテストの入力には，脆弱な版と直った版のロックファイルと，いくつかの例外の一覧を用意する．
`npm`の`package-lock.json`は，1つのパッケージだけを書いた小さなもので足りる．

既存のテストへの影響も考える．
基準値の必須の項目が増えると，どのfixtureが合わなくなるか．

## 2-4 設計書

- `ops/standards.yaml`：止める重大度と，例外の最長の日数を足す．スキーマも直す．
- `ops/exceptions.yaml`とそのスキーマ：例外の一覧を作る．各例外は，識別子，対象，理由，承認者，期限を持つ．
- `ops/items.yaml`：依存関係の脆弱性検査と，例外の申請の2つの項目を足す．
  例外の申請は，開発者からの依頼を受け付ける運用である．『運用設計の教科書』のどの分類に当たるかを考える．
- `ops/runbooks/exception-request.md`：例外にしてよい場合と，申請の手順を書く．
- `.github/CODEOWNERS`：例外の一覧の承認者を足す．

## 2-5 テスト駆動の実装

### gate:sca

Trivyは`node:child_process`の`spawnSync`で実行する．
`stdio: "inherit"`にすると，Trivyの出力がそのまま表示される．

最初は，例外なしで脆弱な版のロックファイルを調べ，失敗することを確かめる．
題材そのものに対して実行すると，仕込まれた脆弱性が見つかる．

```text
pnpm-lock.yaml (pnpm)
=====================
Total: 2 (UNKNOWN: 0, LOW: 0, MEDIUM: 0, HIGH: 2, CRITICAL: 0)

┌─────────┬────────────────┬──────────┬────────┬───────────────────┬───────────────┬──────────────────────────────────────────────────────────────┐
│ Library │ Vulnerability  │ Severity │ Status │ Installed Version │ Fixed Version │                            Title                             │
├─────────┼────────────────┼──────────┼────────┼───────────────────┼───────────────┼──────────────────────────────────────────────────────────────┤
│ lodash  │ CVE-2021-23337 │ HIGH     │ fixed  │ 4.17.20           │ 4.17.21       │ nodejs-lodash: command injection via template                │
│         │                │          │        │                   │               │ https://avd.aquasec.com/nvd/cve-2021-23337                   │
│         ├────────────────┤          │        │                   ├───────────────┼──────────────────────────────────────────────────────────────┤
│         │ CVE-2026-4800  │          │        │                   │ 4.18.0        │ lodash: lodash: Arbitrary code execution via untrusted input │
│         │                │          │        │                   │               │ in template imports                                          │
│         │                │          │        │                   │               │ https://avd.aquasec.com/nvd/cve-2026-4800                    │
└─────────┴────────────────┴──────────┴────────┴───────────────────┴───────────────┴──────────────────────────────────────────────────────────────┘
```

ヒントは次のとおりである．

- 題材のディレクトリを調べるとき，ゲートのテストの入力と`node_modules`は`--skip-dirs`で外す．
- YAMLを書き出すには，`yaml`パッケージの`stringify`を使う．
- `mise run check`はタスクを並列に動かす．ゲートのテストと本物のゲートが同じファイルに書くと，結果が混ざる．
  証跡の置き場所を環境変数で替えられるようにし，ゲートのテストでは一時的な場所を使う．
  `tests/gates/helpers.ts`の`run`も直す．

### gate:exceptions

日付の比較は，`Date.parse`で得たミリ秒の差を1日のミリ秒で割って日数にする．
今日の日付を引数で渡せるようにすると，テストの結果が実行した日に左右されない．

### 仕込まれた脆弱性への対応

1. lodashは，直った版に上げる．

   ```console
   pnpm --filter @app/web add lodash@latest
   ```

2. golang-jwtの脆弱性は，トークンを解析する処理にある．
   `token.go`が解析を呼んでいないことを確かめ，手順書に従って例外を申請する．
3. 例外のプルリクエストを，CODEOWNERSの承認者に承認してもらう．

### CI

`ci.yml`に，`sca`ジョブ(結果をartifactに残す)と`exceptions`ジョブを足す．
`gates`タスクにも2つのゲートを足す．

## 2-6 振り返り

1. 自分の`TESTLIST.md`と解答のテストリストを比べる．
2. 期限を過ぎた例外を，`gate:sca`と`gate:exceptions`の両方で止めるのはなぜか．
3. 「到達しない」を理由にした例外で，期限が要るのはなぜか．
4. 今日の日付を引数にしなかったら，ゲートのテストに何が起きるか．
5. 運用項目と実装を比べ，合わないところがあれば直す．

## 2-7 発展課題

例外の対象が，今の検査の結果に1件も現れなければ失敗する検査を足す．
直った後も例外が残り続けるのを防げる．
テストリスト，設計書，実装の順に進める．
